# 販売管理データで学ぶ機械学習（Sales Analytics）

[![CI](https://github.com/singlestroke8/machine-learning/actions/workflows/ci.yml/badge.svg)](https://github.com/singlestroke8/machine-learning/actions/workflows/ci.yml)

**1つの販売管理データから、性質の違う機械学習の課題を順に解いていく学習記録。**

回帰・分類・クラスタリング・異常検知・推薦を、**同じ型**で扱う。
手法を並べることが目的ではなく、**毎回きちんと検証すること**を示すためのリポジトリである。

コードだけでなく、**なぜその設計にしたか**（[設計判断の記録](docs/adr/)）と
**何に詰まってどう解決したか**（[学習ログ](docs/log/)）を残している。

> **機械学習にお詳しくない方へ**: 数式を使わない説明を
> [`docs/for-business/`](docs/for-business/) に用意しています。

---

## 解いている課題

販売管理データは存在するが、分析されていない、という状況を出発点にしている。

「担当者別」「部署別」「月別」の集計を出すだけなら **Excel のピボットで済む。**
本リポジトリが扱うのはその先である。

> **「今日時点で、今月はいくらで着地するか」**

聞いているのは経営層と、そこから数字をコミットされている管理職である。
詳細は [予測の目的定義](docs/objective.md)。

### 営業と経営で話が噛み合わない理由

同じデータ・同じ手法（直近5営業日の平均）で、集計レベルだけ変えるとこうなる。

| 集計レベル | 系列数 | 外し率 |
| --- | --- | --- |
| 担当者 × 品名 | 150 | **89.3%** ← 営業の「その時々ですよ」は正しい |
| 部署別 | 3 | 59.2% |
| **全社（日次）** | 1 | **44.7%** |
| **全社（月次）** | 1 | **19.8%** ← 経営が見る単位では読める |

**粒度と期間の両方を上げて初めて読めるようになる。**
どちらの立場も自分の見ている単位では正しい。

## 機械学習を使わない範囲も、先に決めている

月次の売上を月初に一度だけ予測するなら、**機械学習は要らない。**

| 方法 | 外し率 | どこでできるか |
| --- | --- | --- |
| 直近3ヶ月の平均 | 30.8% | Excel |
| 前年同月と同じ | 23.9% | Excel |
| **前年同月 × 成長率** | **19.8%** | **Excel（関数2つ）** |

月次データは3年で36点しかなく、機械学習が前年同月比に勝てる余地は小さい。

**ではどこに機械学習が要るのか。** 前年同月比には決定的な欠点がある。

> **月初に出しても月末に出しても、同じ数字しか返さない。**

今日までの受注が例年より2割少なくても、予測は1円も動かない。
一方「今のペースが続く」と単純に外挿すると、月の前半ほど外す。

**「今日までの実績」と「例年のパターン」を、経過日数に応じてどう混ぜるか。**
ここが機械学習の仕事である、と定義している。

## 動かす

前提: [uv](https://docs.astral.sh/uv/)（Python のパッケージ管理）

```bash
# 1. 依存関係
uv sync --extra train

# 2. データ生成 → 合格基準の検査まで一気に行う
uv run sales generate

# 3. データの中身を分析する
uv run python scripts/explore_transactions.py

# 4. 課題①: 売上の着地予測を学習・評価する
uv run sales train-landing
```

`sales generate` は生成して終わりにせず、**そのまま合格基準を検査する。**

```
=== 合格基準の検査 ===
  OK  前年同月比の外し率    19.8%（24ヶ月で評価）
  OK  離反顧客の割合      14.5%
  OK  異常の混入率       0.88%（471 行）
  OK  大型案件の割合      0.60%
  OK  受注の無い部署×月    0 組
  OK  顧客あたり月間受注回数  3.7 回
  OK  通常取引の原価割れ    0 行
```

**基準を満たさなければ終了コード 1 で落ちる。**
「生成できた」と「使えるデータができた」は別だからである。

## データについて

**合成データである。** 実際の取引記録ではない。
東京の1拠点から関東近県の法人顧客に PC とソフトウェアを販売する想定で、
1行 = 1受注の1品目という、実務で受け取るのと同じ形のローデータを作る。

| ファイル | 内容 | 行数 |
| --- | --- | --- |
| `data/raw/transactions.csv` | 取引明細 | 53,231 |
| `data/raw/customers.csv` | 顧客マスタ | 200 |
| `data/raw/anomaly_labels.csv` | 異常の正解（**評価専用**） | 471 |

先頭3ヶ月ぶんのサンプルを [`data/sample/`](data/sample/) に置いてある。

### 何を仕込んでいて、何を仕込んでいないか

季節性・曜日周期・部署の得意商材・関連購買は、**すべて生成器に書き込んである。**
モデルがそれを当てても実力の証明にはならない。

その線引きは [データ理解](docs/data-understanding.md) に分けて記録している。
**結果の数字を読む前に、こちらを読んでほしい。**

### 前身の失敗から直した点

前身のデータは**毎年まったく同じ月係数**を使っていたため、
前年同月比で予測すると外し率 **5.0%** まで当たってしまった。
Excel で足りるデータであり、機械学習の題材にならない。

年ごとの変動・大型案件の偶発・顧客の出入りを入れ、**19.8%** にした。
この値は合格基準として固定してあり、規則的になりすぎるとテストが落ちる。

## 設計上の要点

### 1. 合格基準を、生成する前に決める

前身では、生成したデータに**原価割れの受注が3.0%**混ざっていたことに
しばらく気づかなかった。金額の整合性テストは通っていた。
**計算は合っていたが、符号を見ていなかった。**

いまは検査を `src/sales_analytics/data/validate.py` に置き、
生成のたびに自動で走らせている。基準を満たさなければ落ちる。

### 2. 正解ラベルを、ファイルごと分離する

異常検知の正解は `anomaly_labels.csv` に分けてある。
**学習には使わず、評価にのみ使う。**

実務に正解ラベルは存在しない。同じ扱いをするために、
うっかり特徴量に混ぜられない構造にしている。

### 3. 「1つの列を見れば分かる」データにしない

離反の予兆は、**弱い信号が複数**として現れるようにしている。

| | 値引き上限に対する比 | 平均数量 |
| --- | --- | --- |
| 末期より前 | 0.507 | 21.5 |
| 末期（最後の90日） | **0.542** | **14.0** |

差は小さい。1つの列に閾値を引いても当たらない。

同様に「数量が負なら異常」という素朴な検知は、**7割が誤検知になる**
（通常の返品が混ざっているため）。

### 4. 金額を保持せず、数量と単価から導出する

明細の内部表現（`Line`）は**金額を持たない**。
販売金額・原価・粗利は最後にまとめて計算する。

金額を別々に持つと、数量を書き換えたときに更新し忘れ、
「計算は合っているが業務的にありえない行」が生まれる。
前身の原価割れは、まさにこれが原因だった。

## リポジトリ構成

```
src/sales_analytics/
├── config.py           設定の型付き読み込み
├── data/
│   ├── masters.py      商品・組織・顧客のマスタと、顧客の生涯
│   ├── generator.py    取引明細の生成（異常・返品の注入を含む）
│   └── validate.py     ★ 合格基準の検査
├── features/
│   └── calendar.py     営業日・日本の祝日・カレンダー特徴量
├── models/
│   ├── metrics.py      WAPE・bias・区間カバー率など
│   ├── splits.py       拡大窓の時系列CV
│   ├── encoding.py     カテゴリ列 → 整数コード
│   └── estimator.py    LightGBM 分位点回帰とモデル保存形式
└── tasks/
    └── landing/        課題①: 売上の着地予測
        ├── dataset.py  ★ 学習データの組み立て（リーク防止の中核）
        ├── baselines.py 手作業でできる方法5種
        └── train.py    学習・評価・ベースライン比較

conf/config.yaml        業務設定（期間・顧客数・新規/離反の割合）
data/sample/            サンプルとデータ辞書
docs/objective.md       ★ 何を、誰のために、なぜ予測するのか
docs/data-understanding.md  ★ 何が仕込みで、何が分析結果か
tests/                  テスト88件
```

`models/` の4つは、課題（回帰・分類・…）が変わっても使い回す部品である。
課題ごとの学習ループは、課題を実装する時点で追加する。
**使っていないコードを先回りして置かない**方針にしている。

## 品質保証

| 項目 | 内容 |
| --- | --- |
| テスト | pytest 88件。業務ルール・課題の成立条件・再現性を検査 |
| 型検査 | mypy **strict**（`src` は例外なく通過） |
| 静的解析 | ruff |
| CI | GitHub Actions 2ジョブ：静的解析＋単体テスト / 本番設定での合格基準チェック |

CI では **README に書いた手順をそのまま実行する**ジョブを置いている。
手順書が腐るのは実行されないからなので、CI で実行してしまう方針にした。

## 既知の限界

| 限界 | 内容 |
| --- | --- |
| **合成データである** | 季節性・曜日周期・部署の傾向は生成器に定数で書き込んである。実データで同じ結果が出る保証はない |
| **価格改定が無い** | 定価が期間中まったく変わらない。値上げの影響は分析できない |
| **商談情報が無い** | 失注が記録されていないため、案件別の受注確度は予測できない |
| **地域差が効いていない** | 所在地は分布としてしか入っておらず、購買行動に影響しない |
| **着地予測がベースラインに負けている** | 素朴な手計算（累計＋前年同月の残り按分）に WAPE 0.1724 対 0.1470 で負け。特に価値のある月の前半で負けている → [記録](docs/tasks/01-landing.md) |
| **予測区間が使えない** | 80%区間のはずが実測カバー率 0.422。安全余裕の計算には使えない |
| **課題②〜⑤が未着手** | 分類・クラスタリング・異常検知・推薦はこれから |
