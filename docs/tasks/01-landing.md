# 課題① 売上の着地予測 — 機械学習はベースラインに負けた

- 種類: 回帰・時系列
- 状態: **一巡完了。現時点でベースラインに勝てていない**
- 日付: 2026-08-21

> **結論を先に**: 4通りの定式化を試したが、素朴な手計算（当月の累計 ＋ 前年同月を
> 残り営業日で按分）に勝てなかった。**WAPE 0.1724 対 0.1470 で 17.3% 負け。**
> これ以上の調整は検証データへの過学習になるため、いったん止める。

---

## ① 業務の問い

> **「今日時点で、今月はいくらで着地するか」**

聞いているのは経営層と、そこから数字をコミットされている管理職。
月末になってから分かっても打ち手が無いので、**価値があるのは月の前半**である。

予測の単位は「（部署, 対象月, 経過営業日 k）→ その月の着地額」。
部署3つ＋全社の4系列 × 36ヶ月 × 約20営業日。

---

## ② 手法の選定

| | |
| --- | --- |
| 採用 | LightGBM 分位点回帰（q = 0.1 / 0.5 / 0.9） |
| 理由 | 表形式・数千行。予測区間が要る（経営に点予測だけ出しても使えない） |
| 採らなかった | 深層学習（データが3千行では過剰）、ARIMA等（月次36点では推定できない） |

---

## ③ ベースライン（5種）

**弱い比較相手を選べば改善率はいくらでも大きく書ける。** ここでは手作業でできる
方法のうち、思いつく限り強いものを並べた。

| 方法 | WAPE | 内容 |
| --- | --- | --- |
| 前年同月 × 伸び率 | 0.2934 | **経過日数を使わない**。月初でも月末でも同じ数字 |
| 線形外挿 | 0.1706 | 今のペースが月末まで続くと仮定 |
| **残り按分** | **0.1470** | 累計 ＋ 前年同月を残り営業日で按分 ← **最強** |
| 進捗率外挿 | 0.2617 | 累計 ÷ 前年同期の進捗率 |
| 残り実額 | 0.1647 | 累計 ＋ 前年同月の残り実額 |

**事前の予想は外れた。** 最も筋が良いと考えていた「進捗率外挿」が2番目に弱い。
月初の進捗率は 0.033 しかなく、**これで割ると誤差が25倍に増幅される**ためだった。

「残り実額」も予想より弱い。前年同月の営業日数が今年と違うと、
最終営業日でも残りがゼロにならず、過大に見積もる。

---

## ④ 評価の設計

| 項目 | 内容 |
| --- | --- |
| 主要指標 | WAPE |
| 併記 | bias（上振れ・下振れの偏り）／区間カバー率 |
| 検証 | 拡大窓の時系列CV。3分割 × 検証3ヶ月 |
| 必ず分ける | **経過営業日ごとの精度**（平均は月末の当たりやすい予測に引きずられる） |
| 比較条件 | ベースラインも**同じ検証データ**で測る |

### リーク防止

この課題で最も起きやすい事故は、**k日目の予測にk日目より後の受注を混ぜる**こと。
エラーは出ず、検証の成績だけが良くなる。

特徴量は2種類からしか作らない、という規約にした。

1. 当月の k 日目までの累計（``cum_`` 接頭辞。累積和なので定義上 k 日目まで）
2. 前月以前に確定した実績（``prev_`` 接頭辞）

**この規約は、実際に1件の事故を防いだ。** 下記「見つけた不具合」を参照。

## 4回の定式化と、そこで分かったこと

負けた過程そのものが記録として価値があるので、順に残す。

### 1回目: 着地額を「円」のまま予測 → WAPE 0.1804

学習が成立しなかった。原因は2つ。

- **系列ごとに桁が違う。** 営業2部の月平均が約10億、全社は約38億（20倍の幅）
- **水準が年々上がる。** 月平均 28.6億（2022）→ 46.1億（2024）

**決定木は葉の平均しか返せないので、学習データの範囲を超える値を外挿できない。**
検証期間の高い水準は、構造的に予測できなかった。

### 2回目: 前年同月の着地額で割った比 → WAPE 0.1935

桁の問題は消えたが、まだ負けた。最終営業日を見て理由が分かった。

**この時点では「累計＝着地額」で答えが確定しているのに、モデルの WAPE は 0.138 だった。**
すでに確定している部分まで、木に推測させていた。

### 3回目: 素朴な見込み額に対する補正倍率 → WAPE 0.1614

最終営業日は 0.138 → 0.050 に改善。しかし確定部分を掛け算で歪めるのは変わらない。

### 4回目（現在）: 確定した累計はそのまま足し、残りだけ予測 → WAPE 0.1724

```
着地額 = 当月の累計（確定） ＋ 予測した残り
```

**確定している情報を、モデルに推測させない。** 設計としては最も正しい。
予測区間も「残りの不確実性」だけを表すようになった。

しかし全体の WAPE は3回目より悪化した。**設計の正しさと成績は一致しなかった。**

## 見つけた不具合（リーク検査が捕まえた）

特徴量の1つを、こう書いていた。

```python
pl.col("金額").max().cum_max().over(keys)  # 誤り
```

``.max()`` は**月全体の最大**を返す。つまり k 日目の特徴量に、
k 日目より後の受注が混ざっていた。正しくはこう。

```python
pl.col("金額").cum_max().over(keys)  # 正しい
```

**エラーは出ない。検証の成績だけが良くなる。**
リーク検査（「k日目より後の受注を10倍にしても、k日目の特徴量が変わらないこと」）
が無ければ、気づかないまま「勝った」という結論を出していた。

## なぜ負けたのか（仮説）

断定はできない。検証していない仮説として残す。

| 仮説 | 根拠 |
| --- | --- |
| **学習データが少なすぎる** | 1,960行。前年同月が要るので最初の12ヶ月が使えない |
| **残りの誤差がほぼノイズ** | 残り営業日の受注は、生成器では独立な抽選。ベースラインは
その期待値をほぼ正しく当てており、それ以上の情報が無い可能性 |
| **大型案件が予測不能** | 月7件の大型案件（通常の25〜90倍）は、いつ入るか予測できない |
| **勾配ブースティングが向かない規模** | 3千行で、しかも解が既にほぼ解析式で書ける |

**2番目が正しければ、これは失敗ではなく正しい結論である。**
ただし本リポジトリのデータではノイズフロアを算出できないため、確かめられない。

---

## 次にやるとしたら

**いま真っ先にやってはいけないのは、ハイパーパラメータの調整である。**
検証データを見ながら調整すれば数字は下がるが、それは検証データへの過学習であって
実力ではない。同じ誤りを他人の資料で指摘してきた以上、自分でやるわけにはいかない。

やるなら次の順。

1. **線形モデルで同じことをやる。** 負けたのがデータのせいか、
   勾配ブースティングの使い方のせいかを切り分ける
2. **学習データを増やす。** 期間を5年にすれば、使える行が約2.5倍になる
3. **ノイズフロアを推定する。** 「残りはほぼ予測不能」を確かめる。
   確かめられれば「機械学習は不要」という結論を数字で言える

---

## この結果をどう扱うか

**負けたことを隠さない。** ポートフォリオとしては、勝った数字を並べるより
次の点のほうが価値があると考えている。

- ベースラインを5種類、手作業でできる限り強く作った
- 同じ検証データで比較し、経過日ごと・系列ごとに分けて出した
- 事前の予想（進捗率外挿が最強）が外れたことを記録した
- リーク検査が実際に1件の事故を捕まえた
- **検証データを見ながらの調整をしない**、と決めた

「機械学習を適用したが、素朴な方法に勝てなかった」は実務で普通に起きる。
そのとき**それを正直に言えるか**が問われる。
