# ADR-0002: 学習データに合成データを使う

- 状態: 採用
- 日付: 2026-08-16

## 背景

需要予測の題材として、まず実データの候補を検討した。

- Kaggle の M5 Forecasting（Walmart の日次販売データ）
- Rossmann Store Sales
- 各種の公開 POS データ

いずれも「使うためには Kaggle の認証情報を設定し、規約に同意し、数百MBをダウンロードする」必要がある。
このリポジトリは学習記録であると同時に、第三者に見てもらう前提のものである。
「clone してコマンドを打てば同じ結果が出る」ことが、見せる側にとっても見る側にとっても価値が高い。

## 決定

需要データを合成生成する（`src/demand_forecast/data/generate.py`）。
実データの性質のうち、モデリング上重要なものを明示的に作り込む。

組み込んだ性質:

| 性質 | 実装 |
| --- | --- |
| 系列ごとの水準差 | 店舗×商品ごとに基準需要をランダムに設定 |
| 曜日周期 | 週末が高い曜日プロファイル（系列ごとに揺らぎあり） |
| 年周期 | 年1周期の正弦波（振幅・位相を系列ごとに変える） |
| トレンド | 系列ごとに年率 -18%〜+35% の成長率 |
| 価格弾力性 | `(価格 / 基準価格) ^ 弾力性`、弾力性は -2.4〜-1.1 |
| 販促効果 | 数日〜1週間続く販促期間と、その間の値下げ・露出増 |
| 祝日効果 | 日本の祝日＋年末年始に需要の上乗せ |
| 過分散ノイズ | ガンマ・ポアソン混合（負の二項分布） |

**意図的に組み込まなかった性質**（実データとの差分。誠実に明示する）:

- 欠品による販売数量の打ち切り（「売れなかった」と「在庫が無かった」の区別）
- 新商品の投入・終売による系列の出入り
- 店舗改装・競合出店などの構造変化
- 記録漏れ・入力ミスなどのデータ品質問題

## 理由

- **再現性**: シードを固定すれば誰でも同じデータを得られる。認証情報もダウンロードも不要。
- **性質が既知**: 「曜日周期を入れた」と分かっているので、モデルがそれを捉えられているかを検証できる。
  実データでは「捉えられていないのか、そもそも存在しないのか」の切り分けができない。
- **リポジトリが軽い**: データはコードから再生成できるので、リポジトリに含めなくてよい。
- **系列ごとに独立したシード**: 商品数を増やしても既存系列の値が変わらない設計にした
  （`test_adding_a_sku_does_not_change_existing_series` で保証）。
  規模を変えても過去の実験と比較できる。

### 検討した代替案

| 案 | 退けた理由 |
| --- | --- |
| Kaggle の実データ | 認証情報が必要で、第三者がすぐ再現できない |
| 実データをリポジトリに同梱 | ライセンス上グレー。リポジトリも重くなる |
| 合成データを使わず、データ取得手順だけ書く | 手順書は実行されないと腐る。CI で検証できない |

## 結果

**得たもの**

- `uv sync && uv run dfc generate-data && uv run dfc train` だけで誰でも同じ結果に到達できる
- CI でパイプライン全体を回せる（実データ依存だと CI で学習を回せない）
- モデルが「入れた性質」を捉えられているかを検証できる

**諦めたもの**

- **実データ特有の汚さへの対処経験**。これが最大の欠点である。
  実務では前処理の大半が欠品・記録漏れ・単位の不統一への対処に費やされる。
  この差分は `reports/model_card.md` の「使用上の注意」にも明記し、
  実データに差し替えた際は数字がすべて無意味になることを繰り返し断っている。
- 精度の数字そのものの意味。合成データの WAPE は
  ノイズの入れ方で決まるため、他プロジェクトとの比較には使えない。
  だからこそベースラインとの**相対比較**で語る設計にしている（ADR-0006 参照）。

## 今後

実データへの差し替えは、`data/raw/demand.parquet` を同じスキーマで置き換えるだけでよい設計にしてある
（スキーマは `src/demand_forecast/data/loaders.py` の `DEMAND_SCHEMA`）。
欠品の扱いを加えるときは、この ADR を置き換える新しい ADR を書く。
