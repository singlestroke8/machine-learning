# ADR-0001: 設計判断を ADR として記録する

- 状態: 採用
- 日付: 2026-08-16

## 背景

機械学習のプロジェクトでは、コードを読んでも「なぜそうしたのか」が分からない箇所が多く残る。

- なぜ MAPE ではなく WAPE を主要指標にしたのか
- なぜ横断的なランダム分割ではなく時系列分割なのか
- なぜ点予測ではなく分位点回帰なのか

これらはいずれも、コードを見れば「何をしているか」は分かるが、「他の選択肢を退けた理由」は分からない。
結果として、数か月後の自分や引き継いだ人が同じ検討をやり直すことになる。

また、案件の選考では「何ができるか」と同じくらい「なぜそう決めたか」を問われる。
判断の記録が残っていなければ、その場で思い出しながら話すことになり、説得力を欠く。

## 決定

重要な設計判断を ADR（Architecture Decision Record）として `docs/adr/` に1判断1ファイルで残す。

各 ADR は次の構成をとる。

- **背景**: どういう状況で、何を決める必要があったか
- **決定**: 何を選んだか
- **理由**: なぜそれを選んだか（検討した代替案と、それを退けた理由を含む）
- **結果**: この決定によって何が良くなり、何を諦めたか

一度採用した ADR は書き換えない。判断が変わったときは、新しい ADR を追加して古いものを「置き換え済み」にする。
決定そのものより、「判断が変わっていく過程」のほうが情報量が多いためである。

## 理由

- **粒度が適切**: 1ファイル1判断なので、どこに何が書いてあるか探しやすい。
  README にすべて書くと、README が読まれない長さになる。
- **差分が読める**: Markdown なので、コードと同じフローでレビューできる。
- **腐りにくい**: 「決定した時点の記録」なので、後から状況が変わっても記述が誤りにはならない。
  仕様書と違い、更新し続けなくても価値が落ちない。

### 検討した代替案

| 案 | 退けた理由 |
| --- | --- |
| README に全部書く | 判断が増えるほど README が読まれなくなる。ADR は増えても目次が増えるだけで済む |
| コード内のコメントだけ | 「どのファイルにも属さない判断」（評価指標の選択など）を書く場所がない |
| 外部の Wiki / Notion | コードと乖離する。リポジトリを clone しただけでは読めない |

## 結果

**得たもの**

- 設計判断の理由が、コードと同じ場所に、同じバージョン管理下で残る
- 面談や打ち合わせで「なぜそうしたか」を即座に示せる

**諦めたもの**

- 判断ごとに文書を書く手間。ただし、書きながら考えを整理できるぶん、
  判断そのものの質が上がる面もあり、コストはおおむね相殺されている。
