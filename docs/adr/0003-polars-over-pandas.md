# ADR-0003: データ処理に Polars を使う

- 状態: 採用
- 日付: 2026-08-16

## 背景

特徴量生成では、系列（店舗×商品）ごとの `shift` と移動集計を大量に行う。
本番設定では 約3万行の元データから 約41万行の学習行を作り、
1行あたり 42 個の特徴量を計算する。

pandas と Polars のどちらを使うかを決める必要があった。

## 決定

Polars を使う。pandas は依存に含めない。

## 理由

**1. グループ単位の時系列演算の書き味が良い**

このプロジェクトの中核である「系列ごとのラグ」は Polars では次のように書ける。

```python
pl.col("units_sold").shift(k - 1).over(["store_id", "sku_id"])
```

pandas の `groupby().shift()` はインデックスの扱いが絡み、
`reset_index` や `sort_index` を挟むうちに「どの順序が保証されているのか」が分からなくなりやすい。
時系列でこれが起きると、**エラーにならないままラグがずれる**。最も避けたい種類のバグである。

**2. null と NaN が区別される**

pandas は歴史的経緯から欠損の表現が複数あり、整数列に欠損が入ると float になる。
Polars は null が型と独立しているため、「履歴が足りなくて計算できない」ことを
`Int32` のまま null として表現できる。ラグ特徴量では初期行が必ず欠損するので、この差は小さくない。

**3. 式が遅延評価で、意図しない中間コピーが減る**

`with_columns` に式のリストを渡すと一括で最適化される。
pandas の逐次代入と比べ、メモリ使用量と実行時間の両方で有利になる。

**4. 型検査との相性**

`schema` を明示して DataFrame を作れるので、想定と違う型が入ったら生成時点で落ちる。

### Polars の弱点と、それをどう扱ったか

`Series.max()` や `.item()` の戻り値は、型の上では
「数値 or 日付 or 文字列 or None」という広い union になる。
mypy strict では、この値をそのまま日付演算に使えない。

これに対しては `src/demand_forecast/polars_utils.py` に絞り込みヘルパー
（`as_date` / `as_float`）を置き、境界を1か所にまとめた。
型を無視するのではなく、「ここは日付のはず」という前提を明示し、
違ったら実行時にも落ちるようにしている。

### 検討した代替案

| 案 | 退けた理由 |
| --- | --- |
| pandas | groupby + shift のインデックス事故が怖い。欠損表現も曖昧 |
| pandas + Polars 併用 | 変換のたびに型が崩れる。依存も増える |
| DuckDB（SQL で特徴量生成） | SQL のほうが宣言的で良い面もあるが、テストからの扱いが煩雑になる |

## 結果

**得たもの**

- 系列ごとの時系列演算が、順序の保証を含めて読んで分かる形で書ける
- 41万行 × 42特徴量の生成が 1秒程度で終わる
- 欠損が型を壊さない

**諦めたもの**

- pandas 前提のライブラリとの直接連携。
  LightGBM に渡す直前で `.to_numpy()` するようにして回避している。
- scikit-learn の `Pipeline` / `ColumnTransformer` の利用。
  これらは pandas / numpy 前提なので、前処理は自前の関数で組んでいる。
  ただし本プロジェクトの前処理は「特徴量を作る」ことが中心で、
  スケーリングやエンコーディングのような fit/transform を伴う変換がほとんど無い
  （LightGBM は正規化を必要とせず、カテゴリも整数コードで渡す）ため、
  `Pipeline` を使わない不利益は小さい。
