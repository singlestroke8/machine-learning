# ADR-0010: 時間軸を「ステップ」として扱い、営業日単位の刻みに対応する

- 状態: 採用
- 日付: 2026-08-16

## 背景

法人取引（B2B）のデータを扱うことになった。小売と決定的に違うのは、
**土日祝に受注が発生しない**ことである。

このデータをそれまでの暦日前提のパイプラインに載せる方法は2つあった。

| 案 | 内容 |
| --- | --- |
| A | 暦日を軸のまま維持し、土日祝は ``units_sold = 0`` の行を並べる |
| B | 営業日だけを軸にする（1ステップ = 1営業日） |

案 A は既存コードを一切変えずに済む。土日祝のゼロは「本当に受注が無かった」
事実なので嘘ではなく、曜日が特徴量に入っているのでモデルも学習できる。

しかし次の点で案 B が優れると判断した。

- 行の 33% が構造的なゼロで埋まり、学習の実質的な情報量が落ちる
- 「7日移動平均」が実際には5営業日ぶんの情報しか含まず、窓幅の意味が濁る
- 発注担当が考える単位は「2週間 = 10営業日」であり、営業日で数えるほうが業務に沿う

## 決定

**時間軸を「ステップ」として抽象化し、暦日と営業日のどちらでも同じコードが動くようにする。**

`FeatureConfig.calendar` で切り替える。

| 値 | 意味 | 用途 |
| --- | --- | --- |
| `daily` | 1 ステップ = 1 暦日 | 小売のように毎日売上が立つデータ |
| `business` | 1 ステップ = 1 営業日 | 法人取引のように土日祝に受注が無いデータ |

`horizon`・`lags`・`rolling_windows`・`cv.val_steps` の単位はすべてステップになる。
営業日軸なら `horizon: 10` は「10営業日先（約2週間）」を意味する。

## 実装で変えた3か所

時間軸を変えたときに壊れるのは、次の3か所だけだった。
逆に言えば、ここを直せば残りのコードはそのまま動く。

### 1. origin と target の結合（最重要）

**変更前**は暦日の加算で結合していた。

```python
pl.col("date").dt.offset_by(f"{horizon}d")
```

営業日データでこれをやると、土日を跨いだ瞬間に対応する行が存在せず、
**エラーにならないまま行が落ちる**。金曜 origin の3日先は月曜のはずが、
暦日で数えると日曜になり、その行は無い。

**変更後**は日付に連番（ステップ）を振り、その加算で結合する。

```python
pl.col("step") + horizon
```

これで暦日でも営業日でも同じコードが正しく動く。

### 2. 同一曜日の参照

**変更前**は horizon から固定のオフセットを計算していた。

```python
offset = (-horizon) % 7  # 暦日なら正しい
```

営業日軸では 1週間 = 5営業日なので、素直には `% 5` にすればよさそうに見える。
しかし**これは誤りだった**。祝日のある週は営業日が4日しかなく、
5ステップ前が同じ曜日にならない。

実際にテストで検出した例:

```
2024-07-01（月）から 10 営業日先 → 2024-07-16（火）
  ※ 間に海の日（7/15）があるため、2週間ぶんの10営業日が1日ずれる
```

**変更後**は、曜日ごとに「その曜日で最後に観測した値」を持たせ、
target の曜日を見て行ごとに選ぶ。祝日があっても正確で、
しかも `weekly_period` のような設定が不要になった。

### 3. 時系列CVの期間

**変更前**は暦日で区切っていた（`val_days: 28`）。
営業日データでは28暦日が20営業日しか含まず、設定値と実際の検証量がずれる。

**変更後**はデータに現れる日付を昇順に並べ、その位置で区切る（`val_steps: 20`）。
設定名も `val_days` → `val_steps`、`gap_days` → `gap_steps` に改めた。
単位を偽る名前を残すと、いずれ誰かが暦日だと思って設定する。

## この決定を守るための仕組み

`tests/test_business_calendar.py` に、営業日軸専用の検査を置いた。
暦日で通っているリーク検査が、営業日でも同じように成立するかを見る。

- origin と target の間隔が、**営業日で数えて** horizon と一致すること
- 週をまたぐ horizon の行が落ちずに残っていること
- 同一曜日の参照が、実データと突き合わせて本当に同じ曜日を指していること
- 未来の実績を改変しても、過去の特徴量が変わらないこと
- 学習時と推論時で同じ特徴量が出ること
- 飛び飛びの予測対象日（3営業日先と7営業日先だけ）でも horizon を取り違えないこと
- 営業日軸のモデルに土曜の予測を求めたら弾かれること

読み込み時の検証も、時間軸の種類を受け取るようにした。
暦日データを `business` として読むと土日が「不足」として弾かれるので、
**設定と実データの食い違いが学習前に分かる**。

## 実装中に自分で埋め込んだバグ

ステップ方式に変えた最初の実装では、推論時のステップを
「履歴と予測対象に現れる日付」だけから振っていた。

これだと「3営業日先と7営業日先だけ予測してほしい」という要求で、
2つの対象日が隣り合ったステップとみなされ、**両方とも近い将来として扱われる**。
テストで検出できたが、実運用では静かに間違った予測を返し続ける類のバグだった。

修正後は、履歴の開始から予測対象の末尾までの**欠けのない時間軸**を作り、
その上でステップを振っている。

## 結果

**得たもの**

- 暦日と営業日の両方を、同じパイプラインで扱える
- 営業日データで学習が通り、ベースライン比 28% の改善を確認（WAPE 0.379 対 0.530）
- 同一曜日の参照が、祝日の影響を受けなくなった（暦日側も改善）
- 設定名が単位を正しく表すようになった

**諦めたもの**

- 設定ファイルが2つになった（`conf/config.yaml` = 小売の暦日、`conf/b2b.yaml` = 法人の営業日）。
  時間軸が違う以上、1つの設定で両方を賄うのは無理がある。
- 曜日ごとに中間列を7本持つため、特徴量生成のメモリが少し増える。
  結合後に落としているので、最終的な特徴量の数は変わらない。

**この設計が破綻する条件**

- 系列ごとに営業日が違う場合（海外拠点との混在など）。
  現在は全系列が同じ時間軸を共有する前提で、読み込み時に検証している。
- 週次・月次など、さらに粗い粒度。ステップの考え方自体は使えるが、
  カレンダー特徴量（曜日など）が意味を失うので別途の検討が要る。
