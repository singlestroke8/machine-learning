# ADR-0005: 検証に拡大窓の時系列クロスバリデーションを使う

- 状態: 採用
- 日付: 2026-08-16

## 背景

モデルの精度を見積もる方法を決める必要があった。
`KFold` や `train_test_split(shuffle=True)` は最も手軽だが、時系列では使えない。

理由は単純で、ランダム分割では**未来のデータで学習して過去を予測する**組み合わせが必ず生まれる。
本番でその状況は起こりえないので、検証スコアが実運用より良く出る。
しかも、どれだけ良く出ているかは分からない。

## 決定

拡大窓（expanding window）方式の時系列分割を使う（`src/demand_forecast/models/splits.py`）。

```
fold0: [====== train ======][ val ]
fold1: [======== train ========][ val ]
fold2: [========== train ==========][ val ]
                                          ↑ データ末尾
```

- 学習期間の開始はデータの先頭に固定し、後の fold ほど学習期間を伸ばす
- 検証期間は重ならないように後ろから区切る
- **最新の検証期間がデータ末尾に一致する**ように配置する
- 既定は 3 分割 × 28 日

## 理由

**なぜ拡大窓か（スライド窓ではなく）**

スライド窓（学習期間の長さを固定して前に進める）も候補だった。
拡大窓を選んだのは、本番の運用が「これまでのデータを全部使って再学習する」形になるからである。
検証は本番の状況をなぞるべきなので、学習データが増えていく形にした。

古いデータが有害になるほどの構造変化がある業務なら、スライド窓のほうが妥当になる。
その判断ができるよう、`Fold` は学習期間の開始日も保持している。

**なぜ末尾を必ず検証に含めるか**

「今のデータで今どれだけ当たるか」が知りたい情報だからである。
検証期間を真ん中に置くと、直近の傾向変化を捉えられているかが分からない。

**なぜ gap を既定で 0 にしているか**

一般に、時系列CVでは学習期間と検証期間のあいだに gap を空けてリークを防ぐ。
本プロジェクトでは、特徴量が構造的に `origin = target - horizon` で打ち切られているため
（ADR-0004）、gap を空けなくても検証期間の情報は学習に入らない。

具体的には、学習期間の最後の行（target 日 = 学習終了日 T）が参照するのは `T - horizon` までの実績で、
これは検証期間（T+1 以降）とは重ならない。

ただし、この前提が崩れる特徴量を将来足す可能性はあるので、
`gap_days` は設定として残してある。使わないから消す、ではなく、
「今は 0 でよい理由」をここに書いて残す形にした。

**3 分割 × 28 日にした理由**

- 28 日 = 4週間。曜日周期がちょうど 4 回入るので、特定の曜日に偏った評価にならない
- 3 分割で、標準偏差から「fold 間のばらつき」を見られる最低限を確保
- 分割を増やすと1回あたりの学習時間 × 分割数で試行が遅くなる。
  探索の回転数を落とさない範囲での妥協点

## この決定を守るための仕組み

`tests/test_splits.py` で以下を検査している。

- すべての fold で `train_end < val_start`（学習期間が検証期間より過去）
- 後の fold ほど学習期間が長い（拡大窓であること）
- 検証期間どうしが重ならない
- 最新の検証期間がデータ末尾に一致する
- 期間が足りないときは黙って変な分割を作らず、例外を投げる

## 結果

**得たもの**

- 検証スコアが本番の状況を反映する
- fold 間のばらつき（標準偏差）から、スコアの信頼できる桁数が分かる。
  実測では WAPE 0.2859 ± 0.0126 なので、小数第2位までしか意味がない

**諦めたもの**

- 検証に使えるデータ量。`KFold` なら全データが1度は検証に使われるが、
  この方式では末尾の 84 日ぶんしか検証に使われない。
  正しい見積りのための必要経費と考えている。
- 学習時間。3 分割 + 最終学習で、実質4回学習することになる。
