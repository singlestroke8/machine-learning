# ADR-0006: 主要指標に WAPE を使い、必ずベースラインと理論下限を併記する

- 状態: 採用
- 日付: 2026-08-16

## 背景

需要予測の評価指標には定番が複数ある。どれを「主要指標」にするかで、
モデルの最適化方向も、報告の説得力も変わる。

さらに根本的な問題として、**単独の数字には意味がない**。
「WAPE 0.286 でした」と言われても、それが良いのか悪いのかは誰にも判断できない。

## 決定

**1. 主要指標を WAPE（重み付き絶対パーセント誤差）にする。**

$$\text{WAPE} = \frac{\sum |y - \hat{y}|}{\sum |y|}$$

**2. 単独では報告せず、必ず上下から挟んで示す。**

```
ベースライン (何もしない)  ←──  モデル  ──→  理論下限 (これ以上は不可能)
     0.4107                    0.2859              0.2816
```

**3. バイアス（過大／過小予測の偏り）を必ず併記する。**

## 理由

### なぜ MAPE ではないか

MAPE = 平均(|y - ŷ| / y) は、実需 y が小さい日に発散する。
需要が 1 個の日に 3 個と予測すれば、その1日だけで 200% の誤差になる。

需要予測では「たまにしか売れないSKU」が必ず混ざる。
MAPE を主要指標にすると、モデルはそういうSKUの誤差を潰すことに最適化され、
売上の大半を占める主力SKUの精度を犠牲にする。**ビジネス上の重要度と指標が逆行する。**

WAPE は分母が総需要なので、この問題が起きない。
実需 0 の日が含まれていても発散せず、しかも「需要の大きいSKUほど重く効く」という
在庫の意思決定に沿った重みづけになる。

### なぜ RMSE ではないか

RMSE は誤差を二乗するので、外れ値に強く引っ張られる。
需要データには販促日などの大きなスパイクが必ずあり、
RMSE を最適化すると平常日の精度が犠牲になる。

また RMSE は「単位が個数」なので、SKU をまたいで合算した数字が解釈しにくい。
WAPE は無次元なので、「在庫全体で 28.6% 外している」とそのまま言える。

### 指標の対応表

| 指標 | 扱い | 理由 |
| --- | --- | --- |
| **WAPE** | **主要指標** | ゼロに強い、ビジネス言語に翻訳できる、需要量で重みづけされる |
| MAE | 併記 | 「1日あたり平均何個外すか」で、現場に説明しやすい |
| RMSE | 併記 | 大外しの有無を見る |
| sMAPE | 併記 | 他社事例との比較で使われることがあるため |
| bias | **必ず併記** | 下記 |
| pinball loss | 分位点の評価 | 分位点回帰の学習目的そのもの（ADR-0007） |
| 区間カバー率 | 分位点の評価 | 予測区間が楽観的すぎないかの点検 |
| MAPE | 使わない | 実需が小さい日に発散する |

### なぜバイアスを必ず併記するか

在庫の文脈では、「平均的に何%外すか」より
「上振れに偏っているか下振れに偏っているか」のほうが直接効く。

- 過大予測に偏る → 過剰在庫、廃棄
- 過小予測に偏る → 欠品、機会損失

同じ WAPE でも、この2つはまったく違う結果をもたらす。
実測では bias が **-7.1%**（過小予測寄り）だった。これは偶然ではなく、
中央値予測が右に歪んだ需要分布の平均を下回るために起きる構造的なもので、
`reports/model_card.md` にも注意として明記している。

### なぜベースラインと理論下限で挟むか

**下からベースライン**: モデルが「何もしない」に勝てていなければ、
運用コストを払って導入する理由がない。ここでは3種類を用意した。

| ベースライン | 内容 | 実測 WAPE |
| --- | --- | --- |
| naive | 直近の実績をそのまま横引き | 0.5006 |
| seasonal_naive | 同じ曜日の直近実績 | 0.4823 |
| moving_average | 直近7日の移動平均 | 0.4107 |

重要なのは、ベースラインも**学習済みモデルとまったく同じ特徴量行列から**計算していることである。
参照している情報が origin 時点までに限られている点が揃っているので、比較が公平になる。

**上から理論下限**: 需要は確率的に発生するので、真の平均需要を完全に知っていても
実際の販売数は当てられない。この「原理的に取り除けない誤差」が下限になる
（`src/demand_forecast/analysis.py`、`uv run dfc noise-floor`）。

実測では下限が 0.2816、モデルが 0.2859 だった。
つまり**学習可能な余地の 96.7% を回収済み**で、残りは 0.0043 しかない。

この数字が分かると判断が変わる。ハイパーパラメータを追い込んでも、
最大でも 1.5% しか改善しない。だから次にやるべきは「モデルを磨く」ことではなく、
**「そもそも別の情報源を取りに行く」**（天候、競合価格、SNS など）ことになる。
指標を挟んで示す設計にした最大の見返りがここにある。

## 結果

**得たもの**

- 需要の薄いSKUに引きずられない評価
- 「在庫全体で何%外すか」というビジネス側の言葉での報告
- 「あと何%改善できるのか」を数字で言える
- 改善作業を打ち切る判断ができる

**諦めたもの**

- 他プロジェクトとの数値比較。WAPE の絶対値はデータのノイズ量で決まるため、
  「WAPE 0.28 は良いのか」という問いには答えられない。
  だからこそ相対比較の枠組みを用意した。
- 理論下限の推定は合成データだからできること。
  実データでは同じ手が使えず、別の見積り方（同一条件の繰り返し観測のばらつきなど）が必要になる。
