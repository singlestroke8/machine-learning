# ADR-0008: MLflow で実験を記録し、記録の失敗が学習を止めないようにする

- 状態: 採用
- 日付: 2026-08-16

## 背景

モデルの改善は「パラメータを変える → 回す → 比べる」の繰り返しである。
このとき記録が無いと、次のことが起きる。

- 「先週のほうが良かった気がするが、何を変えたか思い出せない」
- 「この数字はどの設定で出たのか分からない」
- 同じ実験を無自覚に2回やる

比較できない実験は、やっていないのと同じである。

## 決定

**1. MLflow で実験を記録する。**

- パラメータ（horizon、分位点、CV設定、LightGBM のハイパーパラメータ）
- 指標（モデルの CV 平均・標準偏差、全ベースラインの WAPE）
- 成果物（`metrics.json`、`feature_importance.csv`、`model_card.md`）

**2. バックエンドは SQLite（`sqlite:///mlflow.db`）にする。**

**3. MLflow は optional 依存にし、未インストールでも学習は完走する。**

**4. 記録に失敗しても、学習結果は失われない。**

## 理由

### SQLite を選んだ経緯（実際に踏んだ問題）

最初はファイルストア（`./mlruns`）を指定した。MLflow の入門例で最もよく見る形である。
しかし実行すると次のエラーで落ちた。

```
MlflowException: The filesystem tracking backend (e.g., './mlruns') is in
maintenance mode and will not receive further updates.
Please migrate to a database backend (e.g., 'sqlite:///mlflow.db')
```

MLflow 3 系でファイルストアが非推奨（メンテナンスモード）になっていた。
`MLFLOW_ALLOW_FILE_STORE=true` で回避もできたが、
**非推奨のものを環境変数で押し通すのは、問題を先送りするだけ**なので、
素直に SQLite バックエンドへ移行した。

SQLite ならファイル1つで完結し、サーバを立てる必要がない。
チームで共有する段階になったら、設定の `mlflow_tracking_uri` を
リモートのトラッキングサーバに向けるだけで移行できる。

### なぜ optional 依存にしたか

MLflow は依存が重い（Flask、SQLAlchemy、Alembic など多数を引き込む）。
推論サーバにこれらが必要ないのは明らかで、`[project.optional-dependencies].train` に分離した
（ADR-0009）。

同時に、「MLflow が入っていないと学習できない」状態も避けたかった。
実験記録は補助機能であり、学習の本質ではない。
未インストール時は警告を出して先に進む設計にしている。

### なぜ記録の失敗を握りつぶすか

```python
try:
    _log_to_mlflow(cfg, results)
except Exception:
    logger.exception("MLflow への記録に失敗しました（学習結果は保存済みです）")
```

一般論として例外の握りつぶしは避けるべきだが、ここは例外にした。
学習には数分かかる。その最後の記録処理でトラッキング先が落ちていたために
**成功した学習の成果物ごと失われる**のは、明らかに割に合わない。

重要なのは、握りつぶす前に成果物の保存を済ませてある点である。
モデル・指標・モデルカードはすべて MLflow 呼び出しの前にディスクへ書き終えている。
また `logger.exception` でスタックトレースを残しているので、失敗が静かに消えることもない。

### 手元の成果物も併存させる

MLflow に記録すると同時に、`reports/` に生の JSON と CSV も書き出している。
MLflow のUIを開かなくても `cat reports/metrics.json` で確認できるし、
CI が成果物として保存するのもこちらである。
記録の手段を1つに依存させないための冗長化でもある。

## 結果

**得たもの**

- 「どの設定でどの数字が出たか」が後から追える
- ベースラインの数字も一緒に記録されるので、比較の文脈ごと残る
- MLflow が無い環境（CI の一部ジョブ、推論コンテナ）でも動く

**諦めたもの**

- SQLite なので同時書き込みに弱い。並列で複数の学習を回す規模になったら
  トラッキングサーバを立てる必要がある
- MLflow のモデルレジストリ機能は使っていない。
  モデルの配布は `models/model.joblib` を直接コンテナにマウントする形で足りているため
