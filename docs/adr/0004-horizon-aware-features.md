# ADR-0004: 特徴量を horizon 基準で打ち切り、horizon を特徴量として持つ単一モデルにする

- 状態: **保留**（対象コードは 2026-08-21 の目的変更で削除。課題①の実装時に作り直す）
- 日付: 2026-08-16

このリポジトリで最も重要な設計判断。

## 背景

「14日先の需要を予測する」とき、予測を行う時点（origin）で手元にあるのは origin までの実績だけである。
予測対象日（target）の前日の売上は、当然まだ分からない。

ところが素朴に特徴量を作ると、これを簡単に破ってしまう。
「target の前日の売上」をラグ特徴量として入れると、検証スコアは劇的に良くなる。
そして本番では、その特徴量が存在しないので精度が出ない。

時系列予測で最も起きやすく、最も気づきにくい事故である。
**エラーが出ないまま、検証だけが良くなる**ため、気づく手がかりがない。

さらに、1〜14日先を予測するには「何日先か」ごとに扱いが変わる。
これをどう構成するかにも選択肢があった。

## 決定

**1. origin 行と target 行を、必ず horizon 日ずらして結合する。**

特徴量生成を2段階に分ける。

- `features/lags.py`: **origin 時点で確定している**系列特徴量だけを作る（`org_` 接頭辞）
- `features/pipeline.py`: origin 行を horizon 日ずらして target 行に結合する

この結合を `_assemble()` の1か所に閉じ込めた。
特徴量を追加するときも、必ずこの構造の中に入るため、リークの入り込む隙間がない。

```
origin 日 o の特徴量  ──(o + h 日にずらす)──>  target 日 t = o + h の行に結合
```

**2. horizon ごとに別モデルを建てず、horizon を特徴量に持つ単一モデルにする。**

学習行は「(系列, target日, horizon)」の3つ組で1行になる。
horizon 1〜14 について、それぞれ origin をずらした行を作り、縦に積む。
`feat_horizon` を特徴量として渡すことで、モデルは「何日先か」に応じた振る舞いを学習できる。

**3. 価格と販促は target 日の値をそのまま使う。**

これらは「計画値として予測時点で確定している」という業務前提を置いている。
小売では販促計画・価格改定は数週間前に決まるのが通常で、この前提は実務的に妥当である。
前提であることを `pipeline.py` の冒頭に明記した。

## 理由

### 打ち切りの構造化について

代替案は「ラグをすべて horizon 以上にする」（H-safe lags）だった。
つまり horizon=14 なら lag_14, lag_21, lag_28 だけを使う。実装は簡単になる。

しかしこれだと、1日先を予測するときも14日前の情報しか使えない。
実際には1日先の予測には前日の実績が使えるはずで、その情報を捨てるのは大きな損になる。

origin を horizon に応じて動かす方式なら、
horizon=1 の行は「前日までの実績」を、horizon=14 の行は「14日前までの実績」を使う。
どちらも「その時点で本当に手に入る情報」であり、かつ最大限使っている。

### 単一モデルについて

| 方式 | 内容 | 判断 |
| --- | --- | --- |
| recursive | 1日先を予測し、その予測値を入力にして2日先を予測… | 誤差が累積する。14日先では発散しやすい |
| direct（horizon ごとにモデル） | 14個のモデルを別々に学習 | 精度は出るが、学習も配布も監視も14倍。分位点3本と掛けると42モデル |
| **単一モデル + horizon 特徴量** | 1モデルで全 horizon を扱う | **採用** |

単一モデルを選んだ決め手は運用コストである。
14個（分位点込みで42個）のモデルを本番で管理するのは、
このプロジェクトの規模に対して明らかに過剰である。
また、horizon をまたいでデータを共有できるため、1モデルあたりの学習データ量が増える利点もある。

精度面では direct 方式に劣る可能性があるが、
horizon 別の WAPE を必ず出力する設計にして（`reports/metrics.json` の `horizon_wape`）、
「どの horizon で劣化しているか」を常に見えるようにした。
ここが極端に悪化するようなら、その horizon だけ別モデルにする判断もできる。

## この決定を守るための仕組み

判断を文書に書くだけでは守られない。テストで縛った（`tests/test_leakage.py`）。

**1. 未来の実績を書き換えても、過去の特徴量が変わらないこと**

```
cutoff より後の units_sold を10倍に改変 → origin ≤ cutoff の行の特徴量が1ビットも変わらない
```

実装の中身を読むのではなく、外から観測できる性質として検査している。
リファクタリングしてもこの性質は保たれるべきなので、テストが陳腐化しない。

**2. 逆向きの検査**

origin 以前の実績を変えたら特徴量は変わること。
これが無いと「特徴量が実績を全く見ていない」場合にも 1 が通ってしまう。

**3. origin と target の間隔が常に horizon と一致すること**

**4. 学習時と推論時で、同じ行に同じ特徴量が生成されること**

training-serving skew の検査。学習と推論で別の関数を通していれば、いつかずれる。
同じ `_assemble()` を通していることを、値の一致で確認している。

## 結果

**得たもの**

- リークが構造的に入り込めない。特徴量を追加してもこの性質が保たれる
- 学習と推論で前処理が食い違わない
- horizon 1個ぶんのモデルで 1〜14日先すべてを賄える
- horizon 別の精度が常に可視化される

**諦めたもの**

- 学習行数が horizon 倍になる（3万行 → 41万行）。
  LightGBM なら数十秒で終わる規模なので許容した。horizon を 90 日などに伸ばすなら再考が必要。
- horizon ごとに最適化された精度。単一モデルは全 horizon の平均的な当てはまりを狙う。

**前提が崩れる条件**

価格・販促が予測時点で未確定な業務では、この設計はそのまま使えない。
その場合は価格自体を別モデルで予測するか、特徴量から外す必要がある。
