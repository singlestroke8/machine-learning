# 予測の目的定義 — 何を、誰のために、なぜ機械学習で予測するのか

**このドキュメントの位置づけ**: 実装より先に、**解くべき問いを確定させる**ためのもの。
ここが曖昧なまま作ると、動くが誰も使わないものができる。

- 対象読者: 本人／協業者／評価者
- 状態: **確定**（2026-08-17）
- 関連: [プロジェクト全体計画](project-plan.md) ／ [判断ログ](decision-log.md)

---

## 1. 誰の、どの問いに答えるか

### answering する問い

> **「今日時点で、今月（今四半期）はいくらで着地するか」**

聞いているのは**経営層と、経営層から数字をコミットされている管理職**である。

### なぜこの問いなのか

販売管理データは存在するが、分析されていない。ただし
「担当者別」「部署別」「顧客別」「月別」の集計を出すだけなら、
**Excel のピボットテーブルで済む。そこは本プロジェクトの対象ではない。**

本プロジェクトが扱うのは、その先である。

| 立場 | 見ているもの | 言うこと |
| --- | --- | --- |
| 営業担当 | 個別の案件 | 「その時々の状況次第ですよ」 |
| 管理職・経営層 | 部署・全社の合計 | 「今期いくら見込めるのか」 |

**どちらも正しい。** 見ている粒度が違うだけである。
これは感覚の対立ではなく、統計的に説明できる。

### 粒度を上げると読めるようになる（実測）

同じデータ・同じ手法（直近5営業日の平均）で、集計レベルだけ変えた結果。

| 集計レベル | 系列数 | 外し率（WAPE） |
| --- | --- | --- |
| 担当者 × 品名 | 120 | **53.9%** ← 営業の実感どおり読めない |
| 部署 × 品名 | 30 | 47.5% |
| 担当者別 | 12 | 39.6% |
| 部署別 | 3 | 24.0% |
| **全社** | **1** | **17.5%** ← 経営が見る単位では読める |

**集計を上げただけで外し率が 1/3 になる。**
個別案件のばらつきは、束ねると打ち消し合う。

この表は、営業部門と経営層の議論が噛み合わない理由をそのまま説明する。
資料の冒頭に置く。

## 2. 予測の定義

### 予測するもの

| 項目 | 内容 |
| --- | --- |
| **対象** | 売上**金額**（数量ではない） |
| **粒度** | ① 部署別の月次 ② 全社の月次・四半期 |
| **予測の時点** | **月内の各営業日**（月初から月末まで、毎日更新する） |
| **予測する先** | **その月（四半期）の着地額** |
| **出力の形** | 点予測 ＋ 予測区間（例: 着地 1.24億／悪くて 1.05億／良くて 1.41億） |

### 1行の意味

```
（部署, 対象月, 経過営業日 k） → その月の着地額

  例: 営業1部 / 2024年10月 / 10営業日経過時点
      → 「着地 1.24億。80%の確からしさで 1.05億〜1.41億」
```

**「経過営業日 k」が予測の起点**である。k が進むほど実績が積み上がり、
予測は当たりやすくなるはずである。**その改善の様子を必ず出力する**（§5）。

### 予測区間が必須である理由

経営に「今月 1.24億です」とだけ伝えるのは、実務上ほとんど意味がない。
必要なのは**「悪ければどこまで落ちるか」**である。
未達が見えて初めて、期中に手を打てる。

したがって**点予測だけの成果物は、この目的においては失敗**とみなす。

## 3. なぜ機械学習が要るのか（要らない範囲も明示する）

### 要らない範囲

**月次の売上を、月初に一度だけ予測するなら、機械学習は不要である。**

全社の月次売上を、素朴な方法で予測した結果。

| 方法 | 外し率 | どこでできるか |
| --- | --- | --- |
| 直近3ヶ月の平均 | 17.0% | Excel |
| 前年同月と同じ | 7.2% | Excel |
| **前年同月 × 全体の成長率** | **5.0%** | **Excel（関数2つ）** |

加えて、月次データは3年で **36点**しかない。
36点で機械学習を学習させても、前年同月比には勝てない。

**この判断を先に書いておくことが、本プロジェクトの主張の一部である。**
不要な場面で機械学習を提案しない、という立場を明示する。

### 要る範囲

前年同月比には、決定的な欠点がある。

> **月初に出しても月末に出しても、同じ数字しか返さない。**

今日までの受注が例年より2割少なくても、前年同月比の予測は1円も動かない。
**期中に入ってきた実績を一切使っていない**ためである。

では「今のペースが続く」と単純に外挿すればよいか。そうはならない。

| 経過 | 線形外挿（今のペースが続くと仮定） |
| --- | --- |
| 3営業日目 | **17.6%** |
| 5営業日目 | 11.7% |
| 10営業日目 | 8.7% |
| 20営業日目 | 0.9% |

**月の前半ほど当たらない。** 月初の数日は変動が大きく、
そこを3倍・5倍しても意味のある数字にならない。
そして**経営が知りたいのは、まさに月の前半**である。
月末になってから分かっても打ち手がない。

### したがって、機械学習の仕事はこう定義される

> **「今日までの実績」と「例年のパターン」を、
> 経過日数に応じてどの重みで混ぜるかを、データから決めること。**

月初は例年のパターンを重く、月末は実績を重く——という方向は自明だが、
**その配分は部署によっても月によっても違う**（3月の予算消化期と8月では別）。
手作業のルールでは書き切れない。ここが機械学習の適用範囲である。

## 4. 比較相手（ベースライン）

**単独の数字には意味がない。** 次の3つに勝てなければ、この仕組みは不要である。

| # | 方法 | 内容 |
| --- | --- | --- |
| 1 | 前年同月 × 成長率 | 期中の実績を使わない。**最も手強い** |
| 2 | 線形外挿 | 今のペースが月末まで続くと仮定する |
| 3 | 累計 ＋ 前年の残り按分 | 実績と例年を、経過日数で単純に按分する |

**3 が実質的な本命の比較相手**である。
機械学習でやろうとしていることの、手作業版にあたる。
**3 に勝てないなら、機械学習は要らない**という結論になる。

将来的には、もう1つ加えたい。

| 4 | 営業のヨミ（現場の積み上げ予測） | **実務における真のベースライン** |

現場が出している見込み数字に勝てるかどうかが、導入可否の最終判断になる。
ただし本リポジトリのデータには存在しないため、いまは検証できない。

## 5. 評価の設計

| 項目 | 内容 |
| --- | --- |
| 主要指標 | **WAPE**（着地額を何%外したか） |
| 併記する指標 | **bias**（上振れ・下振れどちらに偏るか）／**区間カバー率** |
| 必ず分けて出す | **経過営業日ごとの精度**（3日目・5日目・10日目・15日目・20日目） |
| 検証方法 | 時系列CV（過去にさかのぼり、当時知り得た情報だけで予測する） |

### 経過営業日ごとに出す理由

平均値だけ見ると、**月末の当たりやすい予測に引きずられる**。
20営業日目の予測は誰がやっても当たる（もう終わっているため）。

価値があるのは**月の前半**なので、そこの精度を単独で見えるようにする。
既存の「horizon 別 WAPE」と同じ考え方である。

### bias を必ず見る理由

経営向けの予測では、**外す向きが精度より重い**。

- 上振れに偏る予測 → 未達が続き、予測が信用されなくなる
- 下振れに偏る予測 → 期末に慌てて売上を作る（押し込み販売）を誘発する

**平均して当たっていても、偏っていれば使えない。**

## 6. 成功条件

次がすべて満たされたら「できた」とする。

| # | 条件 | 判定方法 |
| --- | --- | --- |
| 1 | ベースライン3種すべてに勝つ | 同じ検証条件で WAPE を比較 |
| 2 | **月の前半（5〜10営業日目）で勝つ** | 経過日別 WAPE で確認。ここが本丸 |
| 3 | 予測区間が名乗りどおり当たる | 80%区間に実績が80%収まるか |
| 4 | 偏りが許容範囲に収まる | bias の絶対値が一定以下 |
| 5 | 部署別でも成立する | 全社だけ当たっても管理職には使えない |
| 6 | 非エンジニアが読んで理解できる | 説明資料で用途を言えるか |

**「精度が高いこと」は成功条件に入れない。**
データ次第で決まってしまい、本人の力量とは別物であるため。
評価されるのは、**精度をどう定義し、どう検証し、どこを限界と示したか**のほうである。

## 7. やらないこと（明示的に対象外とする）

| やらないこと | 理由 |
| --- | --- |
| 集計レポート（担当者別・顧客別の実績一覧） | Excel のピボットで済む。作る意味がない |
| 個別案件の受注確度予測 | 別の問題。データも別（商談情報が要る） |
| 発注・在庫の最適化 | 本目的の対象外。旧設計はこちらだった |
| 日次・商品単位の需要予測 | 経営層の問いに答えない粒度 |
| 深層学習 | この規模・この形式のデータでは勾配ブースティング木が最適 |

## 8. 前提と、いま検証できないこと

### 現在のデータでは、この目的を正しく検証できない

§3 に載せた「前年同月 × 成長率 = 5.0%」は、**割り引いて読む必要がある。**

いまのデータ生成器は、**毎年まったく同じ月係数**（3月 = 1.80 倍など）を使っている。
前年同月比が当たるのは当たり前で、これは私が仕込んだ構造をそのまま読み出しているだけである
（詳細: [データ理解](data-understanding.md)）。

実務の販売データでは、前年同月比の外し率は **15〜25% 程度**が一般的である。

**したがって、データ生成器から作り直す必要がある。** 具体的には次を入れる。

- 年ごとの景況変動（毎年同じ季節性にしない）
- 大型案件の偶発（月に1件入るだけで着地が大きく動く）
- 顧客構成の変化（新規獲得・取引終了）
- 価格改定

**これを入れないと、機械学習が前年同月比に勝つことはない。**
勝てないのはモデルのせいではなく、データが規則的すぎるためである。

### そのほかの前提

| 前提 | 内容 |
| --- | --- |
| 受注日ベース | 売上計上ではなく受注日で集計する。検収基準の業務には別途調整が要る |
| 返品・キャンセルなし | 現データには存在しない。実データでは着地を押し下げる要因になる |
| 組織変更なし | 部署の統廃合が起きると、過去との比較が成立しない |
| 営業日ベース | 土日祝に受注は発生しない（BtoB の前提） |

## 9. 既存の資産をどう扱うか

前身は「日次・商品単位の需要予測（発注担当向け）」だった。
目的が変わったが、**土台の大半はそのまま使える。**

| 扱い | 対象 |
| --- | --- |
| **そのまま使う** | リーク防止の構造（origin と target の分離）／時系列CV／WAPE・bias・区間・ベースラインの評価枠組み／LightGBM 分位点回帰／テスト・CI・ドキュメント一式 |
| **作り直す** | データ生成器（年ごとの変動を入れる）／予測の単位（日次×商品 → 月×部署の着地額）／特徴量（月内経過日・累計・前年同月との比較） |
| **判断保留** | 発注向けの日次需要予測と推論API。別テーマとして残すか、削るか |

### リーク防止の考え方は、そのまま当てはまる

新しい形でも、事故の形は同じである。

```
経過 k 日目の時点で知り得る情報だけを使う
        ↓
  月末の着地額（target）を予測する
        ↓
  月末の実績は、絶対に特徴量に混ぜない
```

**「月の途中で予測しているのに、その月の最終実績を使ってしまう」**——
これは経営予測で最も起きやすい事故で、しかもエラーが出ない。
既存のテストの考え方をそのまま移植する。
