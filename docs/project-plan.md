# プロジェクト全体計画

**目的**: 機械学習エンジニアとして、エンド企業に提出できるポートフォリオを作る。

このドキュメントは「何を、どの順で、誰が決めるか」を定めたもの。
実装の詳細ではなく、**進め方と役割分担**を扱う。

- 対象読者: 本人（進行管理用）／協業者
- 更新: フェーズが進むたびに改訂する
- 関連: [設計判断の記録](adr/) ／ [判断ログ](decision-log.md) ／ [学習ログ](log/)

---

## 1. 成功条件

「ポートフォリオが完成した」を、次の5点がすべて満たされた状態と定義する。
主観的な「良い感じ」で終わらせないための基準である。

| # | 条件 | 判定方法 |
| --- | --- | --- |
| 1 | 非MLエンジニアが読んで、何の役に立つか理解できる | ML未経験者に読んでもらい、説明なしで用途を言えるか |
| 2 | MLエンジニアが読んで、技術的判断の妥当性を確認できる | ADR を読んで「なぜこの手法か」が追えるか |
| 3 | 第三者が clone して同じ結果を再現できる | CI が README の手順をそのまま実行して通ること |
| 4 | AIに任せきりでないことが記録から分かる | 判断ログに、AIの提案を却下・修正した記録があること |
| 5 | 限界を隠していない | 未解決の課題が README に明記されていること |

**注意**: 「精度が高いこと」は成功条件に入れていない。
データ次第で精度は決まってしまい、本人の力量とは別物だからである。
評価されるのは「精度をどう定義し、どう検証し、どう限界を示したか」のほうである。

## 3. データ準備の要件

### 現行コードが受け付けるスキーマ

`src/demand_forecast/data/loaders.py` の `DEMAND_SCHEMA` が唯一の正である。

| 列 | 型 | 制約 |
| --- | --- | --- |
| `date` | 日付 | **系列ごとに1日刻みで連続**（欠落があると検証で弾かれる） |
| `store_id` | 文字列 | 拠点・支店に相当 |
| `sku_id` | 文字列 | 品名に相当 |
| `units_sold` | 整数 | 0以上（売れなかった日は0で明示） |
| `price` | 小数 | 0より大 |
| `promo_flag` | 0/1 | 販促の有無 |

### 必要量

コード上の制約から逆算した数字。

必要量は、コード上の制約から逆算して確定した。

| | 最低 | **推奨（採用）** |
| --- | --- | --- |
| 期間 | 2年（730日） | **3年（1,096日）** |
| 系列数（拠点×品名） | 10 | **20〜30** |
| 行数 | 7,300 | **22,000〜33,000** |
| 学習行数（×horizon 14） | 102,200 | **307,000〜460,000** |

**期間の根拠**: 移動集計の最大窓が91日、horizon が14日なので系列の先頭105日は
特徴量が揃わない。加えて時系列CVが末尾84日を検証に使う。さらに年周期を学習するには
学習期間内に年周期が2回以上必要で、合計すると約2.5年が下限になる。
3年あれば余裕をもって満たせる。

**系列数の根拠**: 拠点IDと品名IDをカテゴリ特徴量として使うため、
系列が5本未満だとカテゴリがほぼ機能しない。一方で50を超えても、
勾配ブースティング木では学習時間が伸びるだけで得るものが少ない。

**これ以上増やす必要はない。** 過剰なデータ量は学習時間を延ばすだけで、
精度には結びつかない。

### 提供済みCSVの評価（判断済み）

`sales_management_sample.csv` を精査した結果、**そのままでは使えない**と判断した。

| 項目 | 現行システムの前提 | 提供CSV |
| --- | --- | --- |
| 時間粒度 | 日次 | **月次**（`計上月`） |
| 期間 | 1,642日 | 41ヶ月 |
| 行数 | 29,556 | **1,000** |
| 季節性 | 曜日周期・祝日 | いずれも存在しない |

系列粒度別の充足率も低く（品名粒度で74%、顧客×品名で6.9%）、
最良の粒度でも 18系列 × 41ヶ月 = 738行にしかならない。
現行の 411,894行と比べて3桁少ない。

**結論**: 日次データを新規に用意する。詳細は §4 Phase 1。

## 5. 役割分担の原則

### 判断の3分類

| 分類 | 扱い | 例 |
| --- | --- | --- |
| **人が決める** | AIに聞いてもよいが、決定は人。判断ログに残す | 課題設定／評価指標／モデル選定／限界の線引き／トレードオフ |
| **AIが書き、人がレビュー** | AIが実装し、人が「この設計でよいか」を確認 | 特徴量設計／アーキテクチャ／API設計 |
| **AIに任せる** | 動けばよい。レビューは結果ベース | ボイラープレート／テスト実装／CI設定／Dockerfile／整形 |

### 「人が決める」に該当するかの判定

次のいずれかに当てはまるなら、人が決めるべき領域である。

1. **業務知識が要る** — 「価格は予測時点で確定しているか」は、データからは分からない
2. **トレードオフがある** — 精度と運用コスト、どちらを取るかに正解はない
3. **説明責任が発生する** — 「なぜこの指標か」を面談で説明するのは本人
4. **間違えても動いてしまう** — リークは、エラーを出さずに検証だけを良くする

**4番目が最も危険**である。AIは動くコードを書くが、
「動くが間違っている」を検出するのは人の仕事になる。

### AIに任せてはいけない具体例（本プロジェクトで実際に起きたこと）

| 事象 | もし気づかなかったら |
| --- | --- |
| `.gitignore` の `data/` がソースディレクトリ `src/.../data/` まで除外していた | ソースコード11ファイルが欠けたまま push され、誰も動かせないリポジトリになっていた |
| MLflow のファイルストアが非推奨になっていた（AIが古い記事の書き方を再現） | 学習のたびに最後で落ちる |
| 予測区間のカバー率が公称0.80に対し実測0.734 | 「精度が出た」で終わり、在庫計画に使えないモデルを提出していた |

いずれも**動作確認と数字の点検で気づいた**もので、コードレビューだけでは見つからない。

## 6. 非MLエンジニア向けドキュメント一式

企業側の読み手には、ML専門でない人（発注担当・事業部門・人事）が必ず含まれる。
以下を用意する。

| # | ドキュメント | 対象読者 | 内容 | 状態 |
| --- | --- | --- | --- | --- |
| 1 | **プロジェクト概要（1枚）** | 全員 | 何を解決し、どんな効果があるか。図1枚＋箇条書き | 未着手 |
| 2 | **ビジネス課題と効果の説明** | 事業部門 | 欠品・過剰在庫のコスト構造。改善率が金額でどう効くか | 未着手 |
| 3 | **用語集** | 非ML | WAPE・予測区間・ベースライン・リーク等を、数式なしで | 未着手 |
| 4 | **精度の読み方** | 非ML | 「WAPE 0.28」が業務的に何を意味するか。良し悪しの判断基準 | 未着手 |
| 5 | **アーキテクチャ図・データフロー図** | 技術者 | データ→特徴量→学習→推論の流れ | 未着手 |
| 6 | **運用手順書** | 情シス | 再学習の頻度、監視項目、障害時の対応 | 未着手 |
| 7 | **制約と前提の一覧** | 全員 | 何ができて何ができないか | README に部分的に有り |
| 8 | **モデルカード** | 技術者 | モデルの素性と使用上の注意 | **作成済み**（自動生成） |
| 9 | **README** | 全員 | 入口。上記への導線 | **作成済み** |
| 10 | **ADR** | 技術者 | 設計判断の記録 | **作成済み**（9件） |
| 11 | **FAQ** | 全員 | 想定質問と回答 | 未着手 |

### 書き方の原則（非ML向け）

- **数式を使わない。** 必要なら図か例示に置き換える
- **専門用語には必ず言い換えを添える。** 「WAPE（在庫全体で何%外したか）」
- **結論を先に書く。** 経緯は後
- **「できないこと」を明記する。** 過大な期待は後で信頼を損なう

## 8. 直近のアクション

順序に意味がある。上から順に片付ける。

Phase 0 は完了した。データ規模も §3 で確定している（3年 × 20〜30系列）。
以降は上から順に片付ける。

| # | やること | 決めるのは | 所要 |
| --- | --- | --- | --- |
| 1 | データ生成スクリプトを作らせ、精査する | AI＋あなたの検証 | 半日 |
| 2 | 取り込みコードを書き、学習を通す | AI | 半日 |
| 3 | ライセンスファイルを置く | あなた | 5分 |
| 4 | 非ML向けドキュメント #1〜#4 を作る | AI下書き＋あなたの推敲 | 1日 |
| 5 | 予測区間の較正（カバー率 0.734 → 0.80） | AI実装＋あなたの判断 | 半日 |

### 1 であなたが決めること

生成データの業務設定。ここは業務知識の領域なので、AIに丸投げしない。

- 何の商材か（IT機器・消耗品・食品などで需要の形が変わる）
- 拠点構成（何拠点、規模差はあるか）
- 販促の頻度と値引き率
- 曜日周期の向き（法人向けなら平日が高い、小売なら週末が高い）

### 5 を追加した理由

予測区間のカバー率不足（公称 0.80 に対し実測 0.734）は、
理論下限とは無関係の課題であり、**改善の余地が確実にある**。

理論下限までの残りは 0.0043 しかないため、モデルの精度をさらに追うより、
区間の較正で実用可能な水準に持っていくほうが投資対効果が明確に高い。
