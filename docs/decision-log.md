# 判断ログ

**このファイルの目的**: 生成AIを使って開発する以上、「どこまで自分で判断したか」を示せなければ、
成果物は評価の対象にならない。ここには**人間が下した判断**だけを記録する。

[ADR](adr/) との使い分け:

| | ADR | 判断ログ（本ファイル） |
| --- | --- | --- |
| 記録するもの | **設計判断そのもの**（何を選び、なぜか） | **判断の過程**（AIが何を提案し、人がどう介入したか） |
| 読み手 | 技術者 | 本人・評価者 |
| 粒度 | 1判断1ファイル | 時系列で1行ずつ |

記録の基準は次のとおり。**AIの提案をそのまま採用した場合も記録する。**
「検討したうえで採用した」ことと「考えずに流した」ことは違うが、
記録が無ければ後者と区別がつかないためである。

---

## 記録テンプレート

```markdown
### YYYY-MM-DD / 論点のタイトル

- **論点**: 何を決める必要があったか
- **AIの提案**: 生成AIが出した案（複数あれば全部）
- **私の判断**: 採用 / 修正して採用 / 却下 / 保留
- **理由**: なぜそう判断したか。業務知識・トレードオフ・リスクのどれに基づくか
- **結果**: その後どうなったか（後日追記）
```

## 2026-08-16

### 技術スタックの構成

- **論点**: どこまで作り込むか（最小構成／フルMLOps／軽量）
- **AIの提案**: 4案。推奨は「モダン最小構成＋MLOps中核」
- **私の判断**: 提案どおり採用
- **理由**: フルMLOps（DVC・Prefect・ドリフト監視）は、この規模のプロジェクトでは
  見栄えだけの装飾になりやすい。使っていないツールを並べるより、
  少ない道具を使い切っているほうが評価されると判断した。
- **結果**: uv / Polars / LightGBM / MLflow / FastAPI / Docker / CI で構成。過不足なし。

### 学習記録の形式

- **論点**: 学習の記録をどう残すか
- **AIの提案**: 4案（日次ログ／ADR／READMEポートフォリオ化／実験記録）
- **私の判断**: 3つを併用（README・ADR・日次ログ）
- **理由**: 読み手が違う。READMEは初見の人、ADRは技術者、ログは自分と面談相手。
  1つに寄せると、どれかの読み手を取りこぼす。
- **結果**: ADR 10件・学習ログ・実験記録が揃った。

### 提供CSVでの学習を見送り

- **論点**: 提供された `sales_management_sample.csv` で学習を進めるか
- **AIの提案**: 精査結果を提示のうえ、系列粒度（品名／カテゴリ等）と
  目的変数（数量／金額／粗利）の選択を求められた
- **私の判断**: **いったん保留し、データ準備からやり直す**
- **理由**: 月次41ヶ月・1,000行では、日次前提の特徴量（曜日・祝日・7日移動平均）が
  すべて無意味になり、学習行数も3桁足りない。
  動かすことはできても、その数字をポートフォリオに載せる意味がない。
  **「動いた」ことより「意味のある検証ができた」ことを優先すべきと判断した。**
- **結果**: データ要件を定義し、生成方針に切り替え。

### 生成データの業務設定

- **論点**: どんな業務を想定してローデータを作るか
- **AIの提案**: 商材・拠点構成・販促頻度・曜日周期の向きを決めてほしい、という問いかけ
- **私の判断**: **自分で指定した**（PC・ソフトウェア／東京1拠点・関東近県の法人顧客／
  同一顧客の反復取引／担当営業が顧客を持つ／営業1部・営業2部・ソリューション営業部の
  3部署／値引率は顧客ごと）
- **理由**: ここは業務知識の領域で、AIに任せると「ありがちな小売データ」が出てくる。
  実務で扱ったことのある形にしないと、面談で中身を説明できない。
- **結果**: 66,703行の取引明細を生成。部署×品名で30系列。

### 原価割れの受注が混ざっていた

- **論点**: 生成された明細の粗利を点検したところ、3.0%（2,013件）が原価割れしていた
- **AIの提案**: 値引率を顧客ごとの絶対値（最大31%）で与える実装
- **私の判断**: **却下。修正させた**
- **理由**: 原価率78〜85%の商材に31%の値引きをすれば当然赤字になる。
  値引率と原価率が独立に設定されていたことが原因で、
  **業務的にありえないデータで学習しても意味がない**。
  デスクトップPCに至っては11.3%が赤字受注だった。
- **結果**: 品名ごとに値引率の上限（粗利率5%を下回らない）を設けさせ、
  テストで固定させた。**金額の整合性テストは通っていたが、符号を見ていなかった。**

### 時間軸を営業日にする

- **論点**: 法人取引データで土日祝をどう扱うか
- **AIの提案**: 2案。(A) 暦日のまま土日祝を `units_sold = 0` で埋める、
  (B) 営業日だけを1ステップとして扱う。AIは B を推奨
- **私の判断**: **B を採用**
- **理由**: BtoBでは土日祝に受注が発生しない。これは業務の性質であって
  「需要がゼロだった日」ではない。暦日で埋めると行の33%が構造的なゼロになり、
  「7日移動平均」が実質5営業日ぶんの情報しか持たなくなる。
  発注担当が考える単位も「2週間 = 10営業日」である。
- **結果**: 時間軸を「ステップ」として抽象化（[ADR-0010](adr/0010-business-day-timeline.md)）。
  設定1行で暦日／営業日を切り替えられるようになった。
  実装の過程で、暦日前提の結合が**エラーを出さないまま行を落とす**ことと、
  「1週間 = 5営業日」の固定オフセットが祝日のある週でずれることが判明した。

### 小売側の精度がわずかに落ちるのを許容

- **論点**: 同一曜日参照の実装を変えた結果、小売の WAPE が 0.2859 → 0.2869 に悪化した
- **AIの提案**: 差は fold 間の標準偏差 0.0134 の1割以下であり、
  改善とも悪化とも言えない範囲だという説明
- **私の判断**: **悪化を承知で採用**
- **理由**: 固定オフセット方式は暦日でしか成立せず、営業日軸では祝日でずれる。
  片方のデータセットで 0.001 の精度を守るために、
  もう片方で**静かに間違った特徴量を使い続ける**ほうが害が大きい。
- **結果**: 設定項目 `weekly_period` が不要になり、設定が1つ減った。
  実験記録には旧数値も残し、**現行コードでは再現しない**ことを明記した。

### 生成データの傾向が「仕込み」であることを明記する

- **論点**: 生成データを分析して出てくる傾向（3月の予算消化、曜日周期、部署の得意商材）は、
  敢えて傾向が見えるように作ったものか、ルールに従ったランダムか
- **AIの提案**: 分析結果を「発見」として提示していた
- **私の判断**: **前提を明文化させた**
- **理由**: 季節性も曜日周期も生成器に定数で書いてある。
  それをモデルが当てたことを成果として出すのは、読み手を誤らせる。
  **仕込んだものと、仕込んでいないのに出てきたものを分けなければ、
  この成果物は評価の対象にならない。**
- **結果**: [データ理解](data-understanding.md) を作成し、README の先頭から導線を張った。
  分けてみると、粗利率の部署差と値引率の交絡は定数に無い二次的な結果だと分かった。
  **合成データという弱点が、「相関と因果を区別できる」証拠に反転した。**

## 記録漏れを防ぐために

次のいずれかが起きたら、その場で追記する。

- AIの提案を**却下**した、または**修正して**採用した
- AIが提示した選択肢から**選んだ**
- AIが書いたコードの**誤りを見つけた**
- **業務知識に基づく前提**を置いた（「価格は事前に確定している」など）
- **打ち切りの判断**をした（「これ以上やっても効果が薄い」）

逆に、次は記録しなくてよい。

- 誤字修正・整形などの機械的な作業
- AIに書かせたコードが一度で通った、実装上の細部
