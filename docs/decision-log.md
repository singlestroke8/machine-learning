# 判断ログ

**このファイルの目的**: 生成AIを使って開発する以上、「どこまで自分で判断したか」を示せなければ、
成果物は評価の対象にならない。ここには**人間が下した判断**だけを記録する。

[ADR](adr/) との使い分け:

| | ADR | 判断ログ（本ファイル） |
| --- | --- | --- |
| 記録するもの | **設計判断そのもの**（何を選び、なぜか） | **判断の過程**（AIが何を提案し、人がどう介入したか） |
| 読み手 | 技術者 | 本人・評価者 |
| 粒度 | 1判断1ファイル | 時系列で1行ずつ |

記録の基準は次のとおり。**AIの提案をそのまま採用した場合も記録する。**
「検討したうえで採用した」ことと「考えずに流した」ことは違うが、
記録が無ければ後者と区別がつかないためである。

---

## 記録テンプレート

```markdown
### YYYY-MM-DD / 論点のタイトル

- **論点**: 何を決める必要があったか
- **AIの提案**: 生成AIが出した案（複数あれば全部）
- **私の判断**: 採用 / 修正して採用 / 却下 / 保留
- **理由**: なぜそう判断したか。業務知識・トレードオフ・リスクのどれに基づくか
- **結果**: その後どうなったか（後日追記）
```

## 2026-08-16

### プロジェクトの題材を、顧客解約予測から需要予測へ変更

- **論点**: ポートフォリオの題材を何にするか
- **AIの提案**: 4案（需要予測／解約・LTV／与信・不正検知／汎用テンプレート）
- **私の判断**: 需要予測（時系列）を採用
- **理由**: 分類タスクは分かりやすい反面、時系列を正しく扱えるかを示せない。
  需要予測は案件数が多く、かつリークを踏まずに検証できるかが実力差として出る領域であり、
  示せるものが多いと判断した。
- **結果**: リーク防止の設計が本プロジェクトの中核になり、ADR-0004 と
  リーク検査テスト5件という形で最も見せられる部分になった。判断は妥当だった。

### リポジトリを履歴ごと初期化

- **論点**: 既存プロジェクトを畳むとき、履歴を残すか消すか
- **AIの提案**: 3案（ファイルのみ削除して履歴保持／履歴ごと初期化／成果物だけ残す）
- **私の判断**: 履歴ごと初期化
- **理由**: 前身プロジェクトの試行錯誤が混在すると、リポジトリを見た人が
  「今のプロジェクトがどこから始まったか」を追えなくなる。
- **結果**: `master` に旧履歴が残っているため、置き換えの手順は別途必要。未了。

### 技術スタックの構成

- **論点**: どこまで作り込むか（最小構成／フルMLOps／軽量）
- **AIの提案**: 4案。推奨は「モダン最小構成＋MLOps中核」
- **私の判断**: 提案どおり採用
- **理由**: フルMLOps（DVC・Prefect・ドリフト監視）は、この規模のプロジェクトでは
  見栄えだけの装飾になりやすい。使っていないツールを並べるより、
  少ない道具を使い切っているほうが評価されると判断した。
- **結果**: uv / Polars / LightGBM / MLflow / FastAPI / Docker / CI で構成。過不足なし。

### 学習記録の形式

- **論点**: 学習の記録をどう残すか
- **AIの提案**: 4案（日次ログ／ADR／READMEポートフォリオ化／実験記録）
- **私の判断**: 3つを併用（README・ADR・日次ログ）
- **理由**: 読み手が違う。READMEは初見の人、ADRは技術者、ログは自分と面談相手。
  1つに寄せると、どれかの読み手を取りこぼす。
- **結果**: ADR 9件・学習ログ・実験記録が揃った。

### 提供CSVでの学習を見送り

- **論点**: 提供された `sales_management_sample.csv` で学習を進めるか
- **AIの提案**: 精査結果を提示のうえ、系列粒度（品名／カテゴリ等）と
  目的変数（数量／金額／粗利）の選択を求められた
- **私の判断**: **いったん保留し、データ準備からやり直す**
- **理由**: 月次41ヶ月・1,000行では、日次前提の特徴量（曜日・祝日・7日移動平均）が
  すべて無意味になり、学習行数も3桁足りない。
  動かすことはできても、その数字をポートフォリオに載せる意味がない。
  **「動いた」ことより「意味のある検証ができた」ことを優先すべきと判断した。**
- **結果**: データ要件を定義し、生成方針に切り替え。→ 次項

### ディープラーニングを採用しない

- **論点**: 現状のモデルは LightGBM でありDLではない。ポートフォリオの目的と整合しない
- **AIの提案**: 3案（A: GBDTのまま押し切る／B: DLを追加して比較／C: 題材ごと変更）。
  **推奨は B（両方実装して比較）**だった
- **私の判断**: **AIの推奨（B）を却下し、A を採用。ディープラーニングは入れない**
- **理由**:
  1. **そもそもリポジトリがその前提で作られていない。**
     需要予測という題材、表形式・数万行という規模、リーク防止と検証設計を中心に据えた構成は、
     いずれも勾配ブースティング木を前提に組み上げたものである。
     あとからDLを足すのは、目的に合わせて手段を後付けする行為であり、
     「DLを使いたいから使う」という本末転倒になる。
  2. AIが示した理論下限の数字（学習可能な余地の96.7%を回収済み、残り0.0043）を見て、
     **比較実験の結果が事前に予想できると判断した。**
     比較実験の価値は不確実性を減らすことにあるが、その不確実性がすでに小さい。
  3. 工数（550〜800行）を、より効果の大きい課題に回すべきと判断した。
- **結果**: [ADR-0010](adr/0010-no-deep-learning.md) として記録。
  空いた工数を、未解決だった**予測区間の較正**（カバー率 0.734 → 0.80）に充てる方針に変更。
  こちらは理論下限とは無関係の課題であり、改善の余地が確実にある。

**この判断について**: AIは「両方やって比較するのが最善」という一般論を推奨したが、
一般論が当てはまらない具体的な事情（リポジトリの成り立ち、測定済みの伸びしろ）を
持っているのは人間の側だった。**AIの推奨をそのまま受け入れなかった典型例**として記録しておく。

## 記録漏れを防ぐために

次のいずれかが起きたら、その場で追記する。

- AIの提案を**却下**した、または**修正して**採用した
- AIが提示した選択肢から**選んだ**
- AIが書いたコードの**誤りを見つけた**
- **業務知識に基づく前提**を置いた（「価格は事前に確定している」など）
- **打ち切りの判断**をした（「これ以上やっても効果が薄い」）

逆に、次は記録しなくてよい。

- 誤字修正・整形などの機械的な作業
- AIに書かせたコードが一度で通った、実装上の細部
