# データ理解 — このデータで何が言えて、何が言えないか

**このページの目的**: 本リポジトリのデータは合成である。
合成データで出した数字を、実データの分析結果と同じ顔で提示するのは誠実でない。
そこで **「生成器に仕込んだ構造」と「仕込んでいないのに出てきた結果」を分けて記録する。**

読み手が最初に知るべきことは1点。

> **季節性・曜日周期・部署の得意商材・商材の関連購買は、すべて生成器に書き込んである。**
> モデルがこれらを当てるのは当然であり、そこに情報は無い。

数字はすべて次のコマンドで再現できる。

```bash
uv run sales generate
uv run python scripts/explore_transactions.py
```

## 1. 仕込んである構造（分析しても「発見」にはならない）

生成器（`src/sales_analytics/data/masters.py`）の定数と、
データを集計して出てくる数字の対応。

| データから見える傾向 | 生成器の定数 |
| --- | --- |
| 3月に売上が跳ねる | `MONTH_FACTOR` の3月 = 1.80（年度末の予算消化） |
| 4月・8月に落ち込む | 同 4月 0.70 / 8月 0.75 |
| 月曜から金曜へ受注が増える | `WEEKDAY_FACTOR` = (0.90, 1.00, 1.05, 1.10, 1.15) |
| 営業1部は PC が中心 | `DEPARTMENT_AFFINITY["営業1部"]` = PC 1.7 / ソフト 0.4 |
| ソリューション営業部はソフトが中心 | 同 PC 0.35 / ソフト 1.9 |
| PC を買った顧客が Office を買う | `FOLLOW_UP_AFFINITY`（関連購買） |
| 商材ごとの成長率の差 | 品名ごとの `yearly_growth`（デスクトップPCのみ -0.08） |
| 月末に受注が寄る | `MONTH_END_FACTOR` = 1.35（25日以降） |
| 顧客の1〜2割が離反する | `churn_ratio` = 0.18 |

**構造そのものは1対1で書き込まれている。**
集計値が定数とぴったり一致しないのは、複数の要因が掛け合わさるためである。

### 前身との違い — 「素直には読めない」ようにした

前身のデータには決定的な欠陥があった。**毎年まったく同じ月係数を使っていた**ため、
「前年同月 × 成長率」で予測すると外し率 **5.0%** まで当たってしまった。
Excel の関数2つで足りるデータであり、機械学習の題材にならない。

今回は次を入れて、素朴な予測が簡単には当たらないようにしている。

| 入れたもの | 狙い |
| --- | --- |
| 年ごとの水準変動（対数正規） | 前年同月比を当たらなくする |
| 月係数の年ごとの揺らぎ | 「毎年3月が同じ倍率」にしない |
| 大型案件の偶発（月7件、通常の25〜90倍） | 月次の着地を大きく振らせる |
| 顧客の出入り（新規25% / 離反18%） | 構成の変化を作る |

結果、前年同月比の外し率は **19.8%** になった。実務の販売データで
前年同月比が15〜25%外すのと同じ水準である。

**この数値は合格基準として固定してある**（`src/sales_analytics/data/validate.py`）。
生成器を触って規則的になりすぎたら、テストが落ちる。

## 2. 仕込んでいないのに出てきた結果

ここが、このデータで「分析」と呼べる部分である。

### 2-1. 集計レベルを上げると読めるようになる

同じデータ・同じ手法（直近5営業日の平均）で、集計レベルだけ変えた結果。

| 集計レベル | 系列数 | 外し率 |
| --- | --- | --- |
| 担当者 × 品名 | 150 | **89.3%** |
| 部署 × 品名 | 30 | 74.4% |
| 担当者別 | 15 | 84.3% |
| 部署別 | 3 | 59.2% |
| **全社** | **1** | **44.7%** |

**営業担当が「その時々の状況次第ですよ」と言うのは正しい。**
担当者×品名の粒度では9割外す。一方で全社に束ねると誤差が打ち消し合う。

ただし**単調ではない**。担当者別（84.3%）は部署×品名（30系列, 74.4%）より悪い。
1人の担当者に大型案件が1件入ると、その日の数字が跳ねるためである。
「集計すれば必ず良くなる」という単純な話ではない。

### 2-2. 期間も上げないと読めない

上の表はすべて**日次**である。全社ですら44.7%外す。
経営が見る**月次**にすると、同じ全社でも大きく変わる。

| 予測の方法（全社・月次） | 外し率 |
| --- | --- |
| 直近3ヶ月の平均 | 30.8% |
| 前年同月と同じ | 23.9% |
| **前年同月 × 成長率** | **19.8%** |

**「誰の数字か（粒度）」と「いつの数字か（期間）」の両方を上げて初めて読める。**
これは設計していない結果で、大型案件を入れたことの副作用として現れた。

### 2-3. 離反の予兆は「弱い信号が複数」として現れる

離反顧客について、**同じ顧客の中で**末期とそれ以前を比べた結果。

| | 値引き上限に対する比 | 平均数量 |
| --- | --- | --- |
| 末期より前 | 0.507 | 21.5 |
| **末期（最後の90日）** | **0.542** | **14.0** |

値引き要求が強まり、1回あたりが小さくなる。**どちらも差は小さい。**
1つの列に閾値を引いても当たらず、複数の弱い信号を束ねる必要がある。

**この比較には2つの罠があり、どちらも実際に踏んだ。**

1. **離反顧客と継続顧客をそのまま比べると、逆の結論が出る。**
   規模の小さい顧客ほど値引率が低く、かつ離反しやすいという交絡が入る。
   → 同じ顧客の中で比べる必要がある。
2. **生の値引率は商材構成に引きずられる。**
   ソフトは35%まで値引けるが PC は11%程度しか値引けないので、
   商材構成が変わるだけで平均が動く。
   → 商材ごとの値引き上限に対する比で見る必要がある。

いずれも `tests/test_generator.py` にテストとして固定してある。

### 2-4. 「数量が負なら異常」は7割が誤検知

数量が負の行 368 行のうち、異常ラベルが付いているのは 104 行だけである。
残りは**通常の返品**で、業務上まったく正常である。

異常検知の難しさは、異常を見つけることではなく
**珍しいが正常なものを誤検知しないこと**にある。
大型案件（正常）と数量の桁違い（異常）も、金額だけ見ると区別がつかない。

## 4. 実データにあって、ここに無いもの

以下の分析は、**このデータでは何をやっても無意味**である。

| 欠けているもの | できなくなる分析 |
| --- | --- |
| 価格改定（定価は期間中不変） | 値上げの影響測定、価格戦略 |
| 地域差（所在地は分布のみで、購買行動に効かない） | エリア戦略、拠点展開の判断 |
| 担当者の個人差（粗利率は部署でほぼ決まる） | 営業力の評価、教育対象の特定 |
| 構造変化（コロナ・半導体不足のような断絶） | 異常検知の一部、外部要因の分析 |
| 商談・引合の情報（受注に至らなかった案件） | 受注確度の予測、失注分析 |
| 与信・支払遅延 | 与信管理 |

**⑥ 案件別の受注確度予測は、このデータではできない。** 失注が記録されていないためである。
実務でやるなら SFA/CRM 側のデータが要る。

## 5. 予測モデルの評価としてどう見るべきか

季節性・曜日・部署の効果が定数で入っている以上、
モデルがそれを捉えるのは当然であり、次の主張は**成立しない**。

- 「特徴量エンジニアリングによって精度が向上した」
- 「モデルが季節性を発見した」
- 「実務でこの精度が出せる」

一方、**成立する主張**もある。こちらが本リポジトリの主眼である。

- **Excel で足りる範囲と、機械学習が要る範囲を切り分けられること**
- 学習に使ってはいけない情報（異常ラベル）を、構造的に分離していること
- 評価をベースラインで挟み、**どこで手を止めるかを判断できること**
- 相関を見て因果と誤らないこと（§2-3 の交絡）

つまり評価すべきは**精度の数字ではなく、精度を検証する枠組みのほう**である。
