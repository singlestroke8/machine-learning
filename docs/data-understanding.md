# データ理解 — このデータで何が言えて、何が言えないか

**このページの目的**: 本リポジトリのデータは合成である。
合成データで出した数字を、実データの分析結果と同じ顔で提示するのは誠実でない。
そこで **「生成器に仕込んだ構造」と「仕込んでいないのに出てきた結果」を分けて記録する。**

読み手が最初に知るべきことは1点。

> **季節性・曜日周期・部署の得意商材・成長率は、すべて定数として書き込んである。**
> モデルがこれらを当てるのは当然であり、そこに情報は無い。

このページの数字はすべて次のコマンドで再現できる。

```bash
uv run dfc generate-transactions
uv run python scripts/explore_transactions.py
```

## 1. 仕込んである構造（分析しても「発見」にはならない）

生成器（`src/demand_forecast/data/transactions.py`）の定数と、
データを集計して出てくる数字の対応。

| データから見える傾向 | 生成器の定数 |
| --- | --- |
| 3月の売上指数 **1.53**、9月 1.26、12月 1.13 | `MONTH_FACTOR` = 3月 1.80 / 9月 1.35 / 12月 1.10 |
| 4月 0.69、8月 0.82 と落ち込む | 同 4月 0.70 / 8月 0.75 |
| 月曜から金曜へ明細数が単調増加（+36%） | `WEEKDAY_FACTOR` = (0.90, 1.00, 1.05, 1.10, 1.15) |
| 営業1部の売上は PC が 85% | `DEPARTMENT_AFFINITY["営業1部"]` = PC 1.7 / ソフト 0.4 |
| ソリューション営業部はソフトが 78% | 同 PC 0.35 / ソフト 1.9 |
| 売上が年 +6.0% で成長 | 品名ごとの `yearly_growth`（+0.02〜+0.18、デスクトップPCのみ **-0.08**） |
| 月末に受注が寄る | `_MONTH_END_FACTOR` = 1.35（25日以降） |

集計値が定数とぴったり一致しないのは、月要因・曜日要因・月末要因・顧客規模が
掛け合わさるためである。**構造そのものは1対1で書き込まれている。**

### 乱数が担っているのは3か所だけ

```python
scale = rng.gamma(2.0, 0.5)  # 顧客の規模（値引率と受注量の両方を決める）
noise = rng.gamma(6.0, 1 / 6.0)  # 数量の過分散ノイズ（ポアソンの平均に掛ける）
rng.normal(0.0, 0.015)  # 案件ごとの値引率の振れ
```

つまり「ルールに従った完全なランダム」ではなく、
**「決め打ちの構造 ＋ 局所的なノイズ」**である。

## 2. 仕込んでいないのに出てきた結果

ここが、このデータで唯一「分析」と呼べる部分である。
いずれも定数には書いておらず、**構造の掛け算から二次的に生じたもの**である。

### 2-1. 売上1位の部署が、粗利率では最下位

| 部署 | 売上 | 粗利率 |
| --- | --- | --- |
| 営業1部 | 最大 | **14.7〜17.5%** |
| 営業2部 | 中位 | 22.3〜23.9% |
| ソリューション営業部 | 最小 | **31.9〜38.1%** |

粗利率はどこにも定数として書いていない。
`DEPARTMENT_AFFINITY`（部署の得意商材）と `cost_ratio`（PC 0.78〜0.85 /
ソフトウェア 0.40〜0.55）が掛け合わさった結果である。

実務なら「売上目標だけで評価すると、利益を削る行動を促す」という
報告書の主題になる形をしている。

### 2-2. 値引率と数量の相関は、ほぼ交絡である（最重要）

素直に相関を取ると、値引きが数量を押し上げているように見える。

```
値引率 × 数量（そのまま）          : 0.452
値引率 × 数量（顧客×品名で中心化） : 0.026   ← ほぼ消える
顧客の総売上 × 平均値引率          : 0.697   ← 交絡の正体
```

**大口顧客ほど交渉力が強く値引率が高い。かつ大量に買う。**
相関 0.452 の大半はこの経路によるもので、値引き自体の効果ではない。

生成器には確かに価格弾力性（`_DISCOUNT_ELASTICITY = 1.8`）を入れてある。
しかし顧客ごとの値引率のばらつき（`negotiation_power` 由来、0.031〜0.306）に対し、
同一顧客内の振れは標準偏差 0.015 しかない。
**因果の効果は存在するが、顧客間のばらつきに埋もれて観測できない。**

このデータを素直に集計して「値引き施策で数量が伸びる」と結論すると、
実務では**誤った値引き方針を出すことになる**。

これは合成データの欠陥ではない。実データでも必ず起きる構造であり、
本リポジトリで唯一、設計していないのに再現された実務上の罠である。

> **注記**: この交絡は、`negotiation_power` と `size` を同じ `scale` から
> 導出したことの副作用として生じた。生成器を書いた時点では意図しておらず、
> 分析して初めて気づいた。

## 3. 実データにあって、ここに無いもの

以下の分析は、**このデータでは何をやっても無意味**である。

| 欠けているもの | 実測 | できなくなる分析 |
| --- | --- | --- |
| 新規顧客の獲得 | **0 社** / 80 社 | 顧客獲得コスト、成長要因の分解 |
| 顧客の離脱 | **0 社** / 80 社 | チャーン分析、離脱予兆の検知 |
| 価格改定 | 定価が2種類以上ある品名 **0 件** | 値上げの影響測定、価格戦略 |
| 返品・キャンセル | 数量が負の行 **0 行** | 返品率の管理、品質問題の検知 |
| 地域差 | 1社あたり売上が県でほぼ同じ | エリア戦略、拠点展開の判断 |
| 担当者の個人差 | 粗利率が部署でほぼ決まる | 営業力の評価、教育対象の特定 |
| 関連購買 | PC とソフトが独立に選ばれる | クロスセル、バンドル設計 |
| 構造変化 | 3年間まったく定常 | 異常検知、外部要因の影響分析 |

1受注あたりの品目数も 1件/2件/3件がほぼ均等（11,230 / 11,019 / 11,145）で、
実務なら1品目が圧倒的に多いはずの分布とは違う。

## 4. 予測モデルの評価としてどう見るべきか

**甘い。** 曜日・月・部署の効果が定数で入っている以上、
モデルがそれを捉えるのは当然であり、「特徴量が効いた」という結論に情報量は無い。

具体的には、次の主張は**このデータでは成立しない**。

- 「特徴量エンジニアリングによって精度が向上した」
- 「モデルが季節性を発見した」
- 「実務で WAPE 0.38 が出せる」

一方、**成立する主張**もある。こちらが本リポジトリの主眼である。

- リークを構造的に防ぐ仕組みが機能していること（テストで検証済み）
- 時間軸を変えても同じコードが正しく動くこと（暦日／営業日）
- 評価を理論下限とベースラインで挟み、**どこで手を止めるかを判断できること**
- 相関を見て因果と誤らないこと（§2-2）

つまり評価すべきは**精度の数字ではなく、精度を検証する枠組みのほう**である。
この立場は [`project-plan.md` §1](project-plan.md) の成功条件に、
「精度が高いこと」を含めなかった理由と同じである。

## 5. 実データに差し替えるときの注意

`data/raw/demand.parquet` を同じスキーマ（`DEMAND_SCHEMA`）で置き換えれば動く。
ただし差し替えた時点で、次が起きる。

1. **[`experiments.md`](experiments.md) の数字はすべて無意味になる。** 消すか、合成データの結果と明記する
2. **ノイズフロア（理論下限）が出せなくなる。** 真の期待需要を知っている前提が崩れるため
3. **§3 の欠けているものが一気に流れ込む。** 特に系列の出入りと欠品による打ち切りは、
   現在のスキーマ検証（時間軸の連続性を要求する）を通らない

3 が最も影響が大きい。実データを入れる前に、
「売れなかった日」と「在庫が無かった日」を区別する設計が要る。
