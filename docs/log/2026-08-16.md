# 2026-08-16: 需要予測システムをゼロから構築する

店舗×商品の日次需要予測システムを、ゼロから組み上げた1日の記録。

題材に需要予測を選んだ理由は、案件の需要である。分類タスクは題材として分かりやすい反面、
「時系列を正しく扱えるか」を示せない。需要予測・売上予測は案件数が多く、
かつ**リークを踏まずに検証できるかが実力差として出る**領域なので、
示せるものが多いと判断した。

## 今日やったこと

- 需要予測システムの土台を構築
- 合成データ生成器（曜日・年周期・価格弾力性・販促・祝日・過分散ノイズ）
- horizon 整合の特徴量パイプライン（リーク防止の中核）
- 拡大窓の時系列CV、WAPE中心の評価、3種のベースライン
- LightGBM 分位点回帰（q=0.1/0.5/0.9）＋ MLflow 記録
- FastAPI 推論API（予測区間つき）、Docker、GitHub Actions
- テスト 117 件（うちリーク検査 5 件）、mypy strict 通過
- **誤差の理論下限（ノイズフロア）の推定**

## 学んだこと

### 1. リーク防止は「注意する」ではなく「構造で不可能にする」

最初は「ラグ特徴量を作るとき気をつける」つもりでいた。しかしこれは必ず破綻する。
特徴量を追加するたびに毎回同じ注意を払い続けるのは無理だからである。

そこで設計を変えた。**origin（予測基準日）側の特徴量と target（予測対象日）側の行を、
別々に作ってから horizon 日ずらして結合する**形にした。

```
origin 日 o の特徴量  ──(o + h 日にずらす)──>  target 日 t = o + h の行に結合
```

結合は `_assemble()` の1か所だけ。特徴量を増やしても、必ずこの構造の中に入る。
「気をつける」が要らなくなった。

さらに、この性質をテストで縛った。実装を読むのではなく、外から観測できる性質として検査する。

```
cutoff より後の実績を10倍に改変 → origin ≤ cutoff の行の特徴量が1ビットも変わらない
```

この書き方の良いところは、リファクタリングしても陳腐化しないことである。
実装がどう変わっても、この性質は保たれるべきなので。

**対になる逆向きのテストも書いた。** origin 以前の実績を変えたら特徴量は変わること。
これが無いと「特徴量が実績を全く見ていない」場合にも上のテストが通ってしまう。
テストが空振りしていないことを保証する必要がある、というのは今日いちばんの気づきだった。

### 2. horizon をモデル構成にどう組み込むか

1〜14日先を予測する方法は3つある。

| 方式 | 内容 | 判断 |
| --- | --- | --- |
| recursive | 予測値を入力にして次を予測 | 誤差が累積する。14日先で発散しやすい |
| direct | horizon ごとに別モデル（14個） | 精度は出るが、分位点3本と掛けて42モデルの運用は過剰 |
| 単一モデル + horizon 特徴量 | 1モデルで全部 | **採用** |

決め手は運用コストだった。ただし精度面の妥協なので、
**horizon 別の WAPE を必ず出力する**設計にして、どこで劣化しているかを常に見えるようにした。

### 3. 単独の数字には意味がない

「WAPE 0.286 が出ました」と書いても、良いのか悪いのか自分でも判断できないことに気づいた。
上下から挟む必要がある。

```
ベースライン（何もしない） ←── モデル ──→ 理論下限（これ以上は不可能）
      0.4107                   0.2859           0.2816
```

**下からベースライン。** naive / seasonal_naive / moving_average の3つを用意した。
重要なのは、ベースラインも**学習済みモデルとまったく同じ特徴量行列から**計算していること。
参照している情報の範囲が揃っているので比較が公平になる。

**上から理論下限。** これが今日いちばん収穫のあった部分である。
需要は確率的に発生するので、真の平均需要 λ を完全に知っていても実際の販売数は当てられない。
合成データなら λ が分かるので、この「原理的に取り除けない誤差」を計算できる。

やり方は、各 λ について負の二項分布からサンプリングし、
条件付き中央値を予測としたときの平均絶対誤差を集計するだけ（`src/demand_forecast/analysis.py`）。

結果:

```
理論下限 WAPE (真の期待需要を知っていても避けられない誤差): 0.2816
最良ベースライン (moving_average) WAPE: 0.4107
モデル WAPE: 0.2859

  ベースラインからの改善: 30.4%
  学習可能な余地のうち回収した割合: 96.7%
  理論下限までの残り: 0.0043
```

**この数字が判断を変えた。** ハイパーパラメータをどれだけ追い込んでも、
残っている改善余地は最大 1.5% しかない。
だから次にやるべきは「モデルを磨く」ことではなく、
**別の情報源を取りに行く**（天候、競合価格、近隣イベント）か、
**別の課題を解く**（区間の較正）ことになる。

改善作業を「これ以上やっても無駄だ」と判断して打ち切れることは、
実務では精度そのものと同じくらい価値があると思う。

### 4. horizon 別の WAPE が横ばいだった意味

| horizon | 1日 | 7日 | 14日 |
| --- | --- | --- | --- |
| WAPE | 0.2851 | 0.2847 | 0.2873 |

普通なら「先の予測ほど当たらない」はずなのに、ほぼ横ばいだった。
最初はバグを疑ったが、理論下限を計算したあとに納得がいった。

誤差の 98% がノイズフロアで占められている。ノイズは horizon に依存しない。
だから horizon による劣化（0.0022）が、ノイズ（0.2816）に埋もれて見えないだけである。

そしてこれは、**合成データが定常的すぎることの証拠**でもある。
実データなら店舗改装・競合出店・トレンド変化があるので、
先の予測ほど「今の水準の見積り」が外れて劣化が見えるはずである。
横ばいであること自体が、この合成データの限界を示している。
バグではなかったが、データの性質を1つ理解できた。

## 詰まったこと / 解決

### MLflow のファイルストアが廃止されていた

**症状**: 学習は完走したのに、最後の記録処理で落ちた。

```
MlflowException: The filesystem tracking backend (e.g., './mlruns') is in
maintenance mode and will not receive further updates.
Please migrate to a database backend (e.g., 'sqlite:///mlflow.db')
```

**原因**: MLflow 3 系でファイルストア（`./mlruns`）が非推奨になっていた。
入門記事のほとんどが `mlruns` を使っているので、そのまま書いてしまっていた。

**対処**: 2つ直した。

1. バックエンドを SQLite（`sqlite:///mlflow.db`）に変更。
   `MLFLOW_ALLOW_FILE_STORE=true` で押し通すこともできたが、
   非推奨のものを環境変数で回避するのは問題の先送りにしかならない。
2. **記録処理を try/except で囲んだ。**

2 のほうが本質的な学びだった。学習に数分かけたあと、
記録処理の失敗で**成功した学習の成果物ごと失う**のは割に合わない。

```python
try:
    _log_to_mlflow(cfg, results)
except Exception:
    logger.exception("MLflow への記録に失敗しました（学習結果は保存済みです）")
```

握りつぶす前に、モデル・指標・モデルカードはすべてディスクに書き終えてある。
`logger.exception` でスタックトレースも残す。この2つがあれば握りつぶしてよい、
という線引きができた。

**教訓**: 「補助機能の失敗が本体を巻き込まないか」を、書いた直後に自問する。
そして、チュートリアルのコードは新しいバージョンで確認してから使う。

### mypy strict と Polars の相性

**症状**: mypy strict で 125 エラー。ほぼ全部が `[operator]` だった。

```
error: Unsupported operand types for + ("None" and "timedelta")
note: Left operand is of type "int | float | Decimal | date | time | timedelta | str | bytes | ndarray | list | None"
```

**原因**: `Series.max()` や `.item()` の戻り値は、型の上では
「数値 or 日付 or 文字列 or None」という広い union になる。
実行時には1つに決まっているが、型検査器からは何にでもなりうる。

**対処**: 「型検査を諦める」と「全部に `type: ignore` を貼る」の両方を避けたかった。

本体コード（`src/`）には絞り込みヘルパーを作った。

```python
def as_date(value: Any) -> dt.date:
    if isinstance(value, dt.datetime):
        return value.date()
    if isinstance(value, dt.date):
        return value
    raise TypeError(f"日付として扱えない値です: {value!r}")
```

「ここは日付のはず」という前提をコードに書き、違ったら実行時にも落ちる。
`type: ignore` と違って、前提が間違っていたときに気づける。境界も1か所にまとまる。

テスト側は割に合わないと判断し、`tests.*` に限って `operator` を無効化した。
`units.min() >= 0` のような素朴な比較にまでヘルパーを通す価値はない。
**本体は厳しく、テストは緩く**という線引きにして、その理由を pyproject にコメントで残した。

なお、per-module 設定を効かせるには `tests/__init__.py` が必要だった
（無いと mypy が `test_data` のような名前で認識し、`tests.*` にマッチしない）。ここで少し時間を使った。

**教訓**: 型検査が通らないとき、「厳しさを下げる」の前に
「境界に絞り込みを置く」を検討する。多くの場合そのほうが安全で、範囲も狭く済む。

### テストが DuplicateError で落ちた

**症状**: リーク検査を書いたら Polars が落ちた。

```
DuplicateError: projections contained duplicate output name 'feat_horizon'
```

**原因**: `select([*keys, *features])` としていたが、
`keys` に入れた `feat_horizon` は `feature_columns()` が返す特徴量にも含まれていた。単純な重複。

**対処**: `features = [c for c in feature_columns(original) if c not in keys]` に修正。

**教訓**: 内容としては些細だが、テストを書いたことでエラーが出た。
本番コードだけ書いていたら「たまたま動く」まま進んでいた可能性がある。

### 予測区間が公称より狭かった（未解決）

**症状**: 80% 区間のはずが、実測カバー率 0.734。

**原因の見立て**: 分位点回帰の過学習。木の本数を減らした試行（`--fast`、60本）では
カバー率 0.844 と、逆に公称を上回っていた。本設定（400本）では 0.734。
木を増やすほど分位点の推定が学習データに寄り、区間が狭くなる。

**現状**: 未解決。**隠さずモデルカードと README に明記した。**
在庫の安全余裕を過小に見積もることになるので、このまま在庫計画には使えない。

**次の対処案**: conformal prediction による較正。
検証期間の残差分位点から区間を補正する方法で、分布の仮定を置かずにカバー率を保証できる。

**教訓**: 点予測の精度だけ見ていたら気づかなかった。
**区間まで評価軸に入れたから見つかった問題**である。
「良い数字」だけを追うと、こういう欠陥は見えないまま本番に出る。

### .gitignore がソースコードを丸ごと除外していた

**症状**: コミット直前に `git status` を確認したら、
`src/demand_forecast/data/` と `src/demand_forecast/models/` のファイルが1つも載っていなかった。
55ファイルしかステージされていない。

**原因**: `.gitignore` にこう書いていた。

```gitignore
data/          # 生成した需要データを追跡しない
models/        # 学習済みモデルを追跡しない
```

`data/` のように先頭にスラッシュを付けないパターンは、
**リポジトリのどの階層にある `data` ディレクトリにもマッチする**。
生成物を除外したつもりが、同じ名前のソースディレクトリまで巻き添えにしていた。

**対処**: 先頭にスラッシュを付けてリポジトリ直下に限定した。

```gitignore
/data/
/models/
```

**教訓**: 2つある。

1. `.gitignore` でディレクトリを除外するときは、
   同じ名前が他の階層に存在しないかを考える。迷ったら先頭にスラッシュを付ける。
2. **コミット前に `git status` を必ず目で確認する。**
   `git add -A` して `git commit` まで一息に打っていたら、そのまま気づかず push していた。
   push 後に「動かない」と言われて初めて分かる類のミスで、
   ファイル数を数えるだけの数秒で防げる。

### Docker イメージのビルドが検証できなかった

**症状**: `docker build` がレジストリからのイメージ取得で 403。

**原因**: 開発環境のネットワークポリシーでコンテナレジストリへの通信が遮断されていた。
コード側の問題ではない。

**対処**: Dockerfile とマルチステージ構成は書ききったうえで、
**検証できていないことを ADR-0009 に明記した**。
CI の `docker` ジョブでビルドと疎通確認まで行う構成にしてあるので、GitHub 上で初めて検証される。

**教訓**: 検証できていないものを「できている」と書かない。
未検証であることと、どこで検証されるかを書いておけば、読む側が正しく判断できる。

# 追記（同日）: 法人取引データと、営業日の時間軸

小売の合成データで一巡したあと、業務設定に沿った**法人取引（B2B）のローデータ**を
自前で生成し、同じパイプラインに載せた記録。

## やったこと

- 取引明細の生成器（1行 = 1受注の1品目、66,703行）
- 明細 → 日次の系列データへの集計（30系列 × 733営業日）
- **時間軸を「ステップ」として抽象化**し、暦日／営業日を設定1行で切り替え可能に
- 営業日軸専用のテストを追加（テスト 152 件に）
- B2B データでの学習・評価（WAPE 0.3792、ベースライン比 28.5% 改善）

## 学んだこと

### 5. 「土日祝はゼロ」を、ゼロで埋めるか軸から外すか

BtoBでは土日祝に受注が発生しない。これを暦日の軸に載せる方法は2つあった。

| 案 | 内容 |
| --- | --- |
| A | 暦日のまま、土日祝は `units_sold = 0` の行を並べる |
| B | 営業日だけを軸にする（1ステップ = 1営業日） |

A は既存コードを一切変えずに済む。しかも「土日祝はゼロ」は嘘ではない。
それでも B を選んだのは、次の3点による。

- 行の33%が構造的なゼロで埋まり、実質的な情報量が落ちる
- 「7日移動平均」が実際には5営業日ぶんの情報しか含まず、**窓幅の意味が濁る**
- 発注担当が考える単位は「2週間 = 10営業日」で、営業日で数えるほうが業務に沿う

**判断の決め手は精度ではなく、「設定値が業務の言葉と一致するか」だった。**
`horizon: 10` が「10営業日先」を指すなら、業務担当と同じ言葉で会話できる。

### 6. 時間軸を変えたときに壊れるのは3か所だけだった

最初は「暦日前提のコードが全面的に書き換えになる」と身構えたが、
実際に壊れたのは3か所しかなかった。

1. origin と target の結合（日付の加算 → ステップの加算）
2. 同一曜日の参照（固定オフセット → 曜日ごとの列を行単位で選択）
3. 時系列CVの区切り（暦日 → データに現れる日付の位置）

**リーク防止のために結合を1か所に閉じ込めていたことが、ここで効いた。**
結合が散らばっていたら、暦日の加算を全部見つけて直す作業になっていた。
1つの設計判断が、想定していなかった別の変更を安くする、という体験だった。

### 7. 単位を偽る名前は必ず誤設定を招く

CVの設定は `val_days: 28` だった。営業日データではこれが20営業日しか含まない。
`val_days` という名前のまま営業日を入れると、**設定した人は暦日だと思っている**。

`val_days` → `val_steps`、`gap_days` → `gap_steps` に改名した。
名前が単位を偽っていると、いずれ誰か（半年後の自分を含む）が必ず間違える。
コメントで補うのではなく、名前を変えるべき場面だった。

## 詰まったこと / 解決

### 暦日の結合が、営業日データで行を静かに落とす

**症状**: エラーは出ない。学習も通る。ただ行数が想定より少ない。

**原因**: origin と target を `date + horizon 日` で結合していた。
営業日データでは、金曜 origin の3日先は月曜のはずが、
暦日で数えると日曜になり、**その行が存在しない**。存在しない行との結合は
エラーにならず、単に落ちる。

```python
# 変更前: 営業日データでは週をまたぐ行が消える
pl.col("date").dt.offset_by(f"{horizon}d")

# 変更後: 日付に連番を振り、その加算で結合する
pl.col("step") + horizon
```

**リーク検査と同じ「静かに間違う」種類の事故**である。
検証データが減れば、残ったのは予測しやすい行ばかりになり、精度は良く見える。

### 「1週間 = 5営業日」が祝日で成立しない

暦日では同一曜日の参照を `(-horizon) % 7` で計算していた。
営業日なら `% 5` にすればよさそうに見える。**これは誤りだった。**

自分で書いたテストが、実データと突き合わせて検出した。

```
2024-07-01（月）から 10 営業日先 → 2024-07-16（火）
  ※ 間に海の日（7/15）があるため、「10営業日 = 2週間」が1日ずれる
```

祝日のある週は営業日が4日しかない。5ステップ前は同じ曜日にならない。

**解決**: 曜日ごとに「その曜日で最後に観測した値」を7本持ち、
target の曜日を見て行ごとに1本を選ぶ形にした。祝日があっても正確で、
`weekly_period` のような設定項目も不要になった。

**教訓**: 「テストを書いたから安全」ではなく、
**実データと突き合わせるテストを書いたから見つかった**。
`% 5` が正しいという思い込みは、計算式を読み直しても気づけなかった。

### 自分で埋め込んだバグ: 推論時のステップの振り方

ステップ方式の最初の実装では、推論時のステップを
「履歴と予測対象に現れる日付」だけから振っていた。

これだと「3営業日先と7営業日先だけ予測したい」という要求で、
2つの対象日が**隣り合ったステップ**とみなされ、両方とも近い将来として扱われる。

テストで検出できたが、実運用では**静かに間違った予測を返し続ける**類のバグだった。
修正後は、履歴の開始から予測対象の末尾までの**欠けのない時間軸**を作ってから
ステップを振っている。

**教訓**: リークを防ぐ構造を作っても、その構造自体の実装は間違えうる。
「安全な設計」と「安全な実装」は別物である。

### 生成データの3.0%が原価割れしていた

**症状**: 明細の粗利を集計したら、66,703行のうち2,013行（3.0%）がマイナス。
損失額 ¥422M。デスクトップPCに至っては11.3%が赤字受注。

**原因**: 顧客ごとの値引率を絶対値（最大31%）で与えていたが、
商材の原価率は78〜85%ある。両者が独立に設定されていたため、
**構造的に赤字になる組み合わせが発生していた**。

**なぜ既存のテストで見つからなかったか**: 金額の整合性テストは
「単価 × 数量 × (1 - 値引率) = 明細金額」という**算術**を検査していた。
計算は正しい。**符号を見ていなかった。**

**解決**: 品名ごとに値引率の上限（粗利率5%を下回らない）を設け、
「原価割れが1件も無いこと」「上限が品名で異なること」をテストで固定した。

**教訓**: 検算のテストは、業務的な妥当性を保証しない。
「計算が合っている」と「ありえる値である」は別の検査が要る。
